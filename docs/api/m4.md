# M4 API contract: planning

Fixed shape both halves build against, in the M1 to M3 style: routes under `/api`, list bodies are objects with one plural key beside `next_cursor`, timestamps ISO 8601 UTC, ids ULIDs, platform error envelope, and a caller outside a workspace sees 404 never 403. One domain lands here, `planning`, plus the one stream consumer it owns.

Everything is workspace scoped and reached through the M1 authorization dependency at `app/common/api/dependencies/authz.py`. No route here introduces a second way to decide access: a cycle is readable exactly when its team is readable and writable exactly when the caller is a team member, and a project, which is workspace level and shared by one or more teams, follows the rule in Authorization rules below. There is no new capability and no new role.

Route prefixes for the gateway, matching `lambda_domain_path_prefixes` in `terraform/apigateway.tf`:

| Domain | Prefix |
|---|---|
| `planning` | `/api/workspaces/{workspace_id}/cycles`, `/api/workspaces/{workspace_id}/projects`, `/api/workspaces/{workspace_id}/roadmap` |

All three are ordinary siblings of the `issues` and `views` prefixes, so nothing here depends on route specificity the way M3's comment prefix does.

## Routes (`planning` domain)

### Cycles

| Method and path | Body in | Body out | Who |
|---|---|---|---|
| `GET /workspaces/{workspace_id}/cycles` | query `team_id` (required), `status?` (`upcoming`, `active`, `completed`, `cancelled`), `cursor?`, `limit?` (1 to 100, default 50) | `{"cycles": [Cycle], "next_cursor"}` ordered by `start_date` ascending | team reader |
| `POST /workspaces/{workspace_id}/cycles` | `{"team_id", "name", "start_date", "end_date", "goal"?}` | `Cycle`, 201 | team member |
| `GET /workspaces/{workspace_id}/cycles/{cycle_id}` | query `team_id` (required) | `Cycle` | team reader |
| `PATCH /workspaces/{workspace_id}/cycles/{cycle_id}` | `{"team_id"}` plus any of `name`, `start_date`, `end_date`, `goal`, `cancelled` | `Cycle` | team member |
| `DELETE /workspaces/{workspace_id}/cycles/{cycle_id}` | query `team_id` (required) | 204; issues pointing at it keep their `cycle_id` until they are next patched, and the row simply stops resolving | team admin |

`team_id` is required on every single-cycle route because the `planning` table's sort key is `team#<pid>#cycle#<cid>`: without the team the read would be a scan, which design section 2 forbids outside an admin path. It is a query parameter rather than a path segment so a cycle id stays stable in a permalink, exactly as M3 does for a comment's `issue_id`.

Overlapping cycles are allowed. The MVP states no "at most one active cycle" constraint, because enforcing it would need a range read and a conditional write on every create, and a team running two overlapping time boxes is a planning mistake rather than a data one.

### Projects

A project is workspace level and belongs to one or more teams, in the Linear shape: `team_ids` (at least one), an optional `lead_id`, a `start_date` and `target_date`, and one of six statuses. It is reached by its own id; no route needs a team to find it.

| Method and path | Body in | Body out | Who |
|---|---|---|---|
| `GET /workspaces/{workspace_id}/projects` | query `team_id?`, `status?` (`backlog`, `planned`, `in_progress`, `paused`, `completed`, `canceled`), `cursor?`, `limit?` (1 to 100, default 50) | `{"projects": [Project], "next_cursor"}` ordered by `target_date` ascending, undated last | member; only projects on a team the caller can see, and with `team_id` only projects on that team |
| `POST /workspaces/{workspace_id}/projects` | `{"team_ids", "name", "description"?, "lead_id"?, "start_date"?, "target_date"?, "status"?}` | `Project`, 201; `status` defaults to `backlog` | writer on every listed team |
| `GET /workspaces/{workspace_id}/projects/{project_id}` | query `team_id?` | `Project` | reader of any of its teams |
| `PATCH /workspaces/{workspace_id}/projects/{project_id}` | any of `team_ids`, `name`, `description`, `lead_id`, `start_date`, `target_date`, `status` | `Project` | writer on a visible team; writer on every team added or removed |
| `DELETE /workspaces/{workspace_id}/projects/{project_id}` | query `team_id?` | 204; issues keep their `project_id` and the row simply stops resolving | admin of every one of its teams |

Older clients keep working. A body `team_id` alone is read as `team_ids: [team_id]`, and beside `team_ids` it must be one of them. A query or patch `team_id` is checked against the project's visible teams and is a 404 when it is not one of them. A `status` of `done`, on input or on a stored row, reads as `completed`.

`lead_id` must be a workspace member and is cleared with null. `target_date` may not precede `start_date`, checked against the merged row on a patch. `name`, `status` and `team_ids` cannot be set to null.

A project's `status` is explicit rather than derived, because its dates are optional and cannot say whether work began. A cycle's status is derived and a project's is set, and the two shapes say so in their own fields.

### Roadmap

| Method and path | Body in | Body out | Who |
|---|---|---|---|
| `GET /workspaces/{workspace_id}/roadmap` | query `team_id?`, `kind?` (`cycle`, `project`), `cursor?`, `limit?` (1 to 100, default 50) | `{"entries": [RoadmapEntry], "next_cursor"}` ordered by `target_date` ascending, undated last | member; a guest sees only their teams |

The roadmap is one read across the teams the caller can see. Without `team_id` it fans out over exactly those teams, which for a guest is `AuthzContext.team_ids` and for everyone else is the workspace's teams, so there is no cross-team widening and no cross-workspace read by construction: `ws_team` begins with the workspace id.

Each team's cycles are one query on `ws_team-target_date-index`, ranged on the cycle's `end_date`. Projects are workspace level and outside that index, so they are one read of the workspace's `project#` prefix, kept when the caller sees any of their teams (and, with `team_id`, when that team is among them). A shared project appears once, not once per team. Undated entries sort last.

The cursor is a position in the merged order rather than a `LastEvaluatedKey`, for the reason M2 already fixed for the issue fan-out: a merged page has no single last evaluated key to hand back. With exactly one team named the read is still merged the same way, so one code path serves both and a cursor means the same thing either way.

### Issues

The `issues` domain gains two optional attributes rather than the `planning` domain gaining a write path onto an issue.

| Method and path | Change |
|---|---|
| `POST /workspaces/{workspace_id}/issues` | the create body accepts `cycle_id` and `project_id`, both optional and nullable |
| `PATCH /workspaces/{workspace_id}/issues/{issue_id}` | the patch body accepts `cycle_id` and `project_id`, both clearable with null |
| `GET /workspaces/{workspace_id}/issues` | the list query accepts `cycle_id` and `project_id` (repeatable, `none` for unset) and their `cycle_id_not` and `project_id_not` negations, alongside the M2 set |
| `PATCH /workspaces/{workspace_id}/issues` | the bulk patch accepts `cycle_id` and `project_id`, validated per issue exactly as the single patch validates them |

Both are validated against the team the issue is in: a `cycle_id` naming a cycle in another team, or a `project_id` naming a project whose `team_ids` do not include the issue's team, is 422, not a silently dangling pointer. Each validation is one point read on `planning`.

`Issue` gains `cycle_id` and `project_id`, both nullable, and each becomes the range value of the `ws_team-cycle_id-index` and `ws_team-project_id-index` the M2 table already declares and leaves sparse. An issue with neither set stays out of both indexes, which is what keeps an unplanned backlog free in index cost.

The `issues` domain reads `planning` and never writes it. The `planning` domain reads `issues` for nothing at all: it never queries them, and its counts arrive on the stream. That is the "rollups without a second write path into issues" design section 7 names.

### Consumers

| Method and path | Body in | Body out | Who |
|---|---|---|---|
| `POST /events` on `planning-rollup-consumer` | stream records | consumer only; a gateway request 404s | none |

It mounts through `webbpulse.events.register_stream_consumer`, which already guards the gateway case and returns the `ReportBatchItemFailures` envelope, exactly as the M2 rollup and the two M3 views consumers do. It runs the `planning` image under the entrypoint `app.domains.planning.consumers.rollup_entrypoint`.

## Shapes

`Cycle`: `cycle_id` (ULID), `workspace_id`, `team_id`, `name` (1 to 80 chars), `start_date` and `end_date` (`YYYY-MM-DD`, both required, `end_date` never before `start_date`), `goal` (nullable, at most 2000 chars), `cancelled` (boolean, default false), `status` (derived, see below), `counts` (`RollupCounts`), `created_by`, `created_at`, `updated_at`.

`Cycle.status` is derived on read from the dates and the flag, never stored: `cancelled` when the flag is set, otherwise `upcoming` while today is before `start_date`, `active` while today is between the two inclusive, and `completed` once today is past `end_date`. Deriving rather than storing is what keeps a cycle from needing a scheduled write to change state at midnight, and it means the status a reader sees is always the one the dates imply.

`Project`: `project_id` (ULID), `workspace_id`, `team_ids` (the teams the caller can see, in the project's order, at least one), `team_id` (the first of `team_ids`, kept for older clients), `name` (1 to 80 chars), `description` (nullable markdown, at most 8192 bytes), `lead_id` (nullable user id), `start_date` and `target_date` (nullable `YYYY-MM-DD`), `status` (`"backlog" | "planned" | "in_progress" | "paused" | "completed" | "canceled"`, default `backlog`, stored), `counts` (`RollupCounts`, over every issue in the project including issues in teams the caller cannot see), `created_by`, `created_at`, `updated_at`.

`RollupCounts`: `todo`, `in_progress`, `done`, `cancelled`, `total`, each a non-negative integer. The four buckets fold M1's five status categories, which are the team's own and so cannot be counted directly by a consumer that will not read a team's config per record: `backlog` and `unstarted` are `todo`, `started` is `in_progress`, `completed` is `done`, `cancelled` is `cancelled`. `total` is the sum, held as its own attribute so a reader never has to trust that four counters agree.

`RoadmapEntry`: `kind` (`"cycle" | "project"`), `id` (the cycle or project id), `team_id`, `team_ids` (a cycle's one team, or a project's visible teams), `name`, `target_date` (nullable; a cycle's `end_date` or a project's `target_date`), `start_date` (nullable), `status` (the cycle's derived status or the project's stored one), `counts` (`RollupCounts`). A roadmap entry is deliberately a projection rather than the full row: the timeline renders a bar and a count, and a reader wanting the rest has the entity's own route.

## Consumer event contract

### `planning-rollup-consumer`

Source: the `issues` table stream, `NEW_AND_OLD_IMAGES`.

Filter pattern: `{"eventName": ["INSERT", "MODIFY", "REMOVE"]}`. A REMOVE has to be handled, otherwise a deleted issue stays counted against its cycle for good.

Both images are read with `webbpulse.events.deserialize_image(record, "NewImage")` and `"OldImage"`.

What it writes: for each record it computes the `(planning_key, bucket)` pair the old image contributed and the pair the new image contributes, for the cycle and the project independently. When the two differ it decrements the old counter and increments the new one with an atomic `ADD` on the planning row, so two records for the same cycle arriving on different shards do not lose a count to a read-modify-write.

The bucket comes from the issue's status category, which the consumer resolves by reading the team's statuses from `team_config` once per record and caching them for the invocation. That is a read of a table the domain already holds read access to, and it is the only way a status id becomes a category without the issue carrying one.

Counters are clamped at zero on read rather than on write: an `ADD -1` that would take a counter below zero is still applied, because refusing it conditionally would make a redelivery diverge, and the read path reports `max(0, value)`. A counter that drifts is repaired by the next full recount, which the MVP does not schedule and does not need: the drift window is a redelivered decrement, which the idempotency below already prevents.

Idempotency: an `ADD` is not idempotent by itself, so each record's effect is claimed first. The consumer writes `planning#<workspace_id>#<issue_id>#<sequence_number>` into `idempotency` conditional on absence, with a 24 hour TTL, and a record that loses the claim is a no-op. The sequence number is the stream record's own, which is stable across a redelivery of the same record and different for a genuinely later change, so a partial-batch retry re-reads the claim rather than double counting.

Nothing is ever written back into the `issues` table. The `planning` bundle holds `issues` as a read table and does not hold it as a write table, which is the invariant design section 7 names and the one a reviewer should check on the Terraform diff.

Failures raise per record, so only that record enters `batchItemFailures`.

## Tables this project adds

Same notation as M3, per `docs/design.md` section 3.

| Table | PK | SK | GSIs | TTL / stream |
|---|---|---|---|---|
| `planning` | `workspace_id` | `planning_key` (`team#<pid>#cycle#<cid>` or `project#<mid>`) | `ws_team-target_date-index` (hash `ws_team` = `<workspace_id>#<team_id>`, range `target_date`) | none |

The table carries no stream of its own: nothing downstream reads a cycle's changes, and the one async effect in this project flows the other way, off the `issues` stream.

`target_date` is a denormalised attribute rather than the entity's own field: a cycle writes its `end_date` into it and a project writes its `target_date`, so one index orders both kinds on the one date a roadmap draws them at. Only cycles write `ws_team`, so projects sit outside the index: a project is workspace level and read from its own `project#` prefix.

The `issues` table gains no change. Its two indexes `ws_team-cycle_id-index` and `ws_team-project_id-index`, declared in M2 and left sparse, become populated by this project's issue attributes. Its `NEW_AND_OLD_IMAGES` stream now feeds four mappings: the M2 rollup on the `issues` function, the two M3 `views` consumers, and this one. Four readers on one stream is at the point where design section 3's note applies, so a fifth wants EventBridge Pipes rather than a fifth direct reader. That is a post-MVP note, not an M4 change.

Repository bundles:

- `planning` writes `planning`, `idempotency`, `rate-limits`; reads `memberships`, `workspaces`, `users`, `teams`, `team_config`, `issues`.
- `issues` gains `planning` as a read table, so a create or patch can validate a `cycle_id` against the issue's own team.

`planning` reads `issues` and never writes it. That is what keeps the rollup off a second write path into the issue.

## Authorization rules

Every route here depends on the M1 `require(...)` dependency and declares one of the capabilities that already exist. No new `Capability` member is added.

- Cycle reads declare `Capability.WORKSPACE_READ` and then resolve the team from the required `team_id` parameter, checking `AuthzContext.can_see_team(team_id)`, which is a 404 when it is false. That is the same fail-closed shape M2 uses for an issue read and the same indistinguishable 404.
- Cycle writes need the caller to be a team member: workspace `owner`, `admin` or `member`, or a guest holding a membership in that team. A guest outside the team gets 404, never 403.
- Deleting a cycle is a team admin, which is `require_team_admin` resolved against the row's own team. Creating and editing is any team member, because a cycle is planning rather than configuration and the whole team moves it.
- Projects fail closed on their team list. A caller sees a project only when `can_see_team` holds for at least one of its `team_ids`, otherwise it is 404; a guest therefore sees only projects on a team it was invited to, and every response lists only the teams the caller can see.
- Creating a project needs write access (team member, as for a cycle) to every listed team. Editing its fields needs write access to at least one visible team. Changing `team_ids` needs write access to every team added or removed; the patch replaces the caller's visible subset and keeps the teams it cannot see, and it may not leave the project with no team the caller can see (422).
- Deleting a project needs an admin of every one of its teams, because a delete orphans every team's issues; a workspace `owner` or `admin` qualifies through the implied team role. A caller who sees the project but not all of its teams gets 403.
- The roadmap enumerates visible teams from `AuthzContext`: `team_ids` for a guest, the workspace's teams otherwise. A `team_id` a guest cannot see is 404 on the roadmap, not an empty roadmap.
- Setting `cycle_id` or `project_id` on an issue needs nothing beyond the team membership the issue patch already needs. A cycle must be in the issue's own team and a project must list the issue's team, so a cycle never collects another team's issues and a project collects only its own teams' issues.
- The consumer carries no user. It reads the issue images off the stream and writes only counters on the planning rows they name. It never calls `require`, and a gateway request to `/events` is 404 by `register_stream_consumer`'s own guard.

The route-contract fixture and the per-domain route counts are regenerated with this project, per the invariant in design section 2, so the diff on that fixture is the review artifact for whether a route here became public.

## Error codes

Beyond the platform envelope's own `NOT_FOUND`, `FORBIDDEN`, `NOT_AUTHENTICATED`, `CONFLICT` and `VALIDATION_ERROR`:

| Code | Status | When |
|---|---|---|
| `NOT_FOUND` | 404 | The workspace, the team, the cycle or the project is absent, the caller may not see the cycle's team or any of the project's teams, or a legacy `team_id` is not one of the project's visible teams |
| `FORBIDDEN` | 403 | The caller is in the team but is not a member for a write, or not an admin for a delete; for a project, not an admin of every team on delete |
| `VALIDATION_ERROR` | 422 | `end_date` is before `start_date`; a name is blank; a date is not `YYYY-MM-DD`; a project's `target_date` is before its `start_date`, its `lead_id` is not a workspace member, it has no team, or a patch nulls `name`, `status` or `team_ids` or leaves no visible team; a `cycle_id` names a cycle outside the issue's team or a `project_id` names a project not on it |
| `CONFLICT` | 409 | A cycle or project id collides, which is an id reuse rather than a lost race |

## Pagination

Unchanged from M2 and M3: an opaque base64url cursor minted and read by `app/common/api/pagination.py`, carrying the scope it was issued under so a cursor from one query is refused on another. Every list body is `{"<plural>": [...], "next_cursor": string or null}`, and `next_cursor` is null exactly when the set is exhausted.

Cycle lists page on a `LastEvaluatedKey` under the team's own sort key prefix, which is a real index position. The project list reads the workspace's `project#` prefix whole (capped at 1000 rows), filters it by visibility, and pages on an offset, as the roadmap does.

## Platform gaps

Verified against `webbpulse` 0.43.0 as installed. Most of design section 6 has landed. What M4 wanted and did not find:

| Gap | Where | Proposed surface |
|---|---|---|
| Atomic multi-counter update | `webbpulse-python` | `Repository.increment` moves one attribute by one delta and answers the new value. The rollup moves two counters on one row in one call, one down and one up, so the product writes the `ADD` expression by hand. `Repository.add(key, {"todo": -1, "in_progress": 1})` beside `increment` closes it, and every rollup consumer in the org wants the same shape. |
| List envelope with one plural key | `webbpulse-python` | Still open from M2 and M3. `http.CursorPage` renders items under `items`, and every list body in this product is an object with one plural key, so `cursor_page` is called with an item key the package builds a model around. Noted again because M4 adds three more list bodies through it. |
| Stream record sequence number | `webbpulse-python` | The consumer's idempotency key needs the record's own `dynamodb.SequenceNumber`, which it reads out of the raw mapping because `deserialize_image` returns only an image. `webbpulse.events.record_sequence(record)` beside it is three lines and every idempotent stream consumer needs it. |
| Derived status from a date range | not a platform gap | A cycle's `upcoming`, `active`, `completed` is product semantics and stays in the product. |

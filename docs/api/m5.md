# M5 API contract: integrations

Fixed shape both halves build against, in the M1, M2 and M3 style: routes under `/api`, list bodies are objects with one plural key, timestamps ISO 8601 UTC, ids ULIDs, platform error envelope, and a caller outside a workspace sees 404 never 403. One domain lands here, `integrations`, plus two SQS consumers it owns.

This is the first milestone with routes that are not reached by a signed-in human. Two of them carry no authorizer at all, and each one names what stands in for identity: the webhook route is authenticated by GitHub's HMAC over the raw body, the callback by a signed `state` this product minted. Everything else is the M1 authorization dependency unchanged, and no new `Capability` member is added.

Route prefixes for the gateway, matching `lambda_domain_path_prefixes` in `terraform/apigateway.tf`:

| Domain | Prefix | Authorizer |
|---|---|---|
| `integrations` | `/api/workspaces/{workspace_id}/github` | JWT |
| `integrations` | `/api/workspaces/{workspace_id}/webhooks` | JWT |
| `integrations` | `/api/workspaces/{workspace_id}/projects/{project_id}/github-transitions` | JWT |
| `integrations` | `/api/workspaces/{workspace_id}/issues/{issue_id}/github-links` | JWT |
| `integrations` | `/api/github` | NONE |

`/api/github` sits outside the workspace prefix because neither route under it has a workspace to put in a path: the webhook's workspace is resolved from the installation id after the signature verifies, and the callback's from the `state` it carries. Both are declared as their own route keys rather than swept into a proxy, so the diff on `terraform/apigateway.tf` is where a reviewer reads which routes are unauthenticated.

Two prefixes route to `integrations` under another domain's subtree. `/api/workspaces/{workspace_id}/issues/{issue_id}/github-links` is more specific than `issues`'s own `/api/workspaces/{workspace_id}/issues/{proxy+}`, and `/api/workspaces/{workspace_id}/projects/{project_id}/github-transitions` is more specific than `projects`'s `{proxy+}`, so API Gateway HTTP API picks each on specificity rather than on declaration order, exactly as M3's comment prefix does.

## Routes (`integrations` domain)

### Install

| Method and path | Body in | Body out | Who |
|---|---|---|---|
| `GET /workspaces/{workspace_id}/github/install-url` | none | `InstallUrl` | workspace admin |
| `GET /workspaces/{workspace_id}/github/installation` | none | `Installation` or 404 when the workspace has none | workspace admin |
| `DELETE /workspaces/{workspace_id}/github/installation` | none | 204; forgets the local rows only | workspace admin |
| `GET /workspaces/{workspace_id}/github/repositories` | none | `{"repositories": [Repository]}` | workspace admin |
| `GET /github/callback` | query `state` (required), `installation_id` (required), `setup_action?` | 302 to the workspace settings page | nobody; the `state` is the credential |
| `POST /github/webhooks` | the GitHub event body | 202 with `{"accepted": true}`, or 200 with `{"accepted": false}` on a replay | nobody; the signature is the credential |

`GET .../github/install-url` returns the App's own install URL with a signed expiring `state` bound to the workspace. Nothing is written: an install that is never completed leaves no row, which is why the state is a signed token rather than a stored nonce.

`DELETE .../github/installation` removes `install#<iid>`, every `repo#<rid>` and every `link#<pr_node_id>` for this workspace. It does not call GitHub. Uninstalling the App is done on GitHub, and the frontend links there, because revoking an installation is the App owner's action and not something an access token from this product is allowed to do on their behalf. The `installation` webhook's `deleted` action performs the same local cleanup when the owner uninstalls from GitHub's side, so the two paths converge on the same state whichever one is used.

### Webhook endpoints

| Method and path | Body in | Body out | Who |
|---|---|---|---|
| `GET /workspaces/{workspace_id}/webhooks` | none | `{"webhooks": [WebhookEndpoint]}` | workspace admin |
| `POST /workspaces/{workspace_id}/webhooks` | `{"url", "events"?, "description"?}` | `WebhookEndpoint` plus `secret` once, 201 | workspace admin |
| `PATCH /workspaces/{workspace_id}/webhooks/{webhook_id}` | any of `url`, `events`, `description`, `active` | `WebhookEndpoint` | workspace admin |
| `POST /workspaces/{workspace_id}/webhooks/{webhook_id}/rotate` | none | `WebhookEndpoint` plus a new `secret` once, 200 | workspace admin |
| `DELETE /workspaces/{workspace_id}/webhooks/{webhook_id}` | none | 204 | workspace admin |

### Transition rules

| Method and path | Body in | Body out | Who |
|---|---|---|---|
| `GET /workspaces/{workspace_id}/projects/{project_id}/github-transitions` | none | `{"transitions": [Transition]}` ordered by `position` | project reader |
| `POST /workspaces/{workspace_id}/projects/{project_id}/github-transitions` | `{"trigger", "status_id", "position"?}` | `Transition`, 201 | project admin |
| `PATCH /workspaces/{workspace_id}/projects/{project_id}/github-transitions/{transition_id}` | any of `trigger`, `status_id`, `position` | `Transition` | project admin |
| `DELETE /workspaces/{workspace_id}/projects/{project_id}/github-transitions/{transition_id}` | none | 204 | project admin |

A project with no rows of its own uses the defaults from design section 4 rather than doing nothing, so an install works before anyone configures it. The defaults are computed rather than seeded: seeding would write five rows per project at create time and leave a project that predates M5 without them, and it would make "this project uses the defaults" indistinguishable from "somebody configured exactly the defaults".

### Issue links

| Method and path | Body in | Body out | Who |
|---|---|---|---|
| `GET /workspaces/{workspace_id}/issues/{issue_id}/github-links` | none | `{"links": [IssueLink]}` newest first | project reader |

Read through `ws_issue-link-index`, so an issue's linked pull requests are one index query rather than a scan of the workspace's links.

## Shapes

`InstallUrl`: `url` (the App's install URL carrying `state`), `state` (the signed token, returned so a test and the frontend can assert what was minted), `expires_at`.

`Installation`: `installation_id` (GitHub's numeric id, as a string), `account_login`, `account_type` (`"User" | "Organization"`), `repository_selection` (`"all" | "selected"`), `installed_by`, `installed_at`, `html_url` (the settings page on GitHub where the owner uninstalls).

`Repository`: `repository_id` (GitHub's numeric id, as a string), `full_name` (`owner/name`), `name`, `private` (bool), `default_branch`, `project_id` (nullable; which project of this workspace the repository's keys are matched against, null meaning every project of the workspace), `linked_at`.

`WebhookEndpoint`: `webhook_id` (ULID), `workspace_id`, `url` (`https` only, at most 2048 chars), `events` (list from `OUTBOUND_EVENTS`, default all of them), `description` (nullable, at most 200 chars), `active` (bool, default true), `secret_hint` (the last four characters of the secret, so a list can tell two endpoints apart without holding either), `created_by`, `created_at`, `updated_at`. `secret` is present only on the create and rotate responses and never stored in a readable form.

`Transition`: `transition_id` (ULID), `project_id`, `trigger` (one of `TRIGGERS`), `status_id` (a status of this project), `position` (integer, ascending), `is_default` (true when this row is one of the computed defaults rather than something stored), `created_at`.

`IssueLink`: `link_id` (the pull request's GitHub node id, which is what the row's sort key carries), `issue_id`, `issue_key`, `repository_full_name`, `pr_number`, `pr_title`, `pr_url`, `pr_state` (`"open" | "closed" | "merged" | "draft"`), `author_login`, `magic_word` (nullable, the word that will close the issue on merge), `applied_status_id` (nullable, the status this link last drove the issue to), `comment_id` (nullable, the GitHub comment this product posted), `check_run_id` (nullable), `linked_at`, `updated_at`.

`TRIGGERS`: `"pr_opened"`, `"pr_ready_for_review"`, `"pr_merged"`, `"pr_closed"`. The defaults are `pr_opened` to the lowest-position `started` status, `pr_merged` to the lowest-position `completed` status, and `pr_closed` to no status at all, which is why a closed-unmerged pull request moves nothing.

`OUTBOUND_EVENTS`: `"issue.created"`, `"issue.updated"`, `"issue.status_changed"`, `"comment.created"`.

## The GitHub App flow

### Install

`GET .../github/install-url` mints a token through the same `webbpulse.security.create_token` the M3 upload ticket uses, under the same `SECRET_KEY` and a distinct audience `standupless.github-install`, carrying `workspace_id` and `user_id` and expiring in 600 seconds. The URL is `https://github.com/apps/<GITHUB_APP_SLUG>/installations/new?state=<token>`.

`GET /github/callback` verifies the token, which is the whole of its authentication: the route reaches no authorizer and reads no membership, so a forged or expired state is a 400 and nothing else happens. It then mints an installation access token from the App private key, reads the installation and its repositories, writes `install#<iid>` and one `repo#<rid>` per repository, and redirects to `<frontend>/workspaces/<workspace_id>/settings/github`.

Minting an installation token is two steps and both are in `app/domains/integrations/github_api.py`: a short-lived RS256 App JWT signed with the private key through PyJWT, which is already a dependency, then `POST /app/installations/<iid>/access_tokens` with that JWT, which answers a token good for an hour. The token is never stored and never logged.

### Webhook receipt

`POST /github/webhooks` reads the raw body before anything parses it, verifies `X-Hub-Signature-256` with `webbpulse.http.verify_hmac_signature` against `GITHUB_WEBHOOK_SECRET`, and answers 401 with no detail when it does not match. An unverified body is never logged and never parsed, which is the order design section 2 fixes.

`X-GitHub-Delivery` is then claimed in `idempotency` under scope `github-delivery` with the existing 24 hour TTL. A claim that loses is a replay and short-circuits to 200 with `{"accepted": false}`, doing nothing else. A claim that wins enqueues the delivery to the `github-events` queue and answers 202.

Nothing in this route calls GitHub and nothing reads a workspace. The delivery id is claimed under the sentinel workspace `_platform`, because the workspace is not known until the consumer resolves the installation and a claim that had to wait for that resolution would put a GSI read on the unauthenticated path.

An event whose type is outside `HANDLED_EVENTS` is answered 202 and dropped without being enqueued, so an App configured with more events than this product handles costs a signature check rather than a queue message.

### Consumers

| Consumer | Source | Effect |
|---|---|---|
| `integrations-events-consumer` | SQS `github-events` | Resolve the workspace, extract keys, write links, apply transitions, write activity, enqueue write-back |
| `integrations-dispatch-consumer` | SQS `webhook-dispatch` | GitHub write-back and outbound signed webhooks |
| `integrations-stream-consumer` | `issues` and `comments` streams | Enqueue outbound webhook jobs to `webhook-dispatch` |

All three mount through `webbpulse.events.register_stream_consumer`, which already guards the gateway case and returns the `ReportBatchItemFailures` envelope. All three run the `integrations` image under their own entrypoint.

Both queues carry a dead-letter queue at `maxReceiveCount` 5. A message that has exhausted its receives is a delivery the product could not make, and it belongs somewhere an operator can read it rather than being retried forever or dropped.

#### `integrations-events-consumer`

Resolves the workspace from the payload's `installation.id` through `installation_id-index`. A delivery whose installation matches no row is dropped without raising: the App was installed on a workspace that has since removed it, and retrying would never resolve.

Key extraction runs over the branch name, the pull request title, the pull request body and every commit message in a push, case-insensitively against each linked project's own `key_prefix` read from `projects`, never a global regex. The pattern per project is `\b<PREFIX>-(\d+)\b` with `re.IGNORECASE`. A key naming a project the installation is not linked to is dropped, which for a repository row carrying a `project_id` means that project alone and otherwise every project of the workspace.

Magic words are `Fixes`, `Closes` and `Resolves`, plus their `-ed` and `-es` forms as GitHub accepts them, and they count only in the pull request title and body, never in a commit message, so a rebase cannot reclose an issue.

Transitions apply the project's rows from `project_config`, falling back to the computed defaults. A transition never overrides a manual status change made after the pull request event: the consumer compares the issue's `updated_at` against the delivery's own timestamp and skips when the issue moved later. That comparison is why the enqueued envelope carries the event's timestamp rather than the consumer reading the clock.

An applied transition writes one `field_changed` activity row with `actor_kind` `"github"`, which is the kind M2 already declared for exactly this.

Every link write and every transition then enqueues a write-back job to `webhook-dispatch`.

#### `integrations-dispatch-consumer`

Two job kinds on one queue, told apart by the envelope's `name`.

`github.writeback` posts the pull request comment listing the linked issues and sets a check run, both with an installation token. Each is skipped when the link row already carries that state: a link whose `comment_id` is set has its comment edited rather than a second one posted, and a check run whose recorded conclusion already matches is not set again. That skip is what makes the job safe to retry.

`webhook.deliver` delivers one outbound event to one endpoint through `webbpulse.events.webhooks.WebhookDispatcher`, which signs the envelope, retries under its own policy and calls the dead-letter hook once when every attempt has failed. The dead-letter hook logs and raises, so the record enters `batchItemFailures` and SQS redelivers it; a message that exhausts its receives lands on the dead-letter queue.

An endpoint is skipped when it is inactive or does not subscribe to the event. A delivery is never attempted from the request path: design section 4 fixes that everything after signature verification is async, and the same rule covers a product event, which is why the issues and comments domains emit nothing synchronously.

#### `integrations-stream-consumer`

The issue and comment domains must not call a queue from a request handler, so the outbound events come off the tables' own streams instead. This consumer reads the `issues` and `comments` streams, tells them apart with `webbpulse.events.source_table`, maps a record to zero or more outbound event names, reads the workspace's endpoints, and enqueues one `webhook.deliver` job per subscribed endpoint.

Mapping: an `issues` INSERT is `issue.created`; an `issues` MODIFY whose `status_id` changed is `issue.status_changed` and any other MODIFY is `issue.updated`; a `comments` INSERT is `comment.created`. A REMOVE produces nothing and is filtered at the event source mapping.

A workspace with no endpoints reads one query and enqueues nothing, which is the common case and is why the endpoint read happens here rather than in the dispatch consumer: one read per record instead of one per endpoint per record.

## Tables this milestone adds

Same notation as M2 and M3, per `docs/design.md` section 3.

| Table | PK | SK | GSIs | TTL / stream |
|---|---|---|---|---|
| `github` | `workspace_id` | `github_key` (`install#<iid>`, `repo#<rid>`, `link#<pr_node_id>`, `webhook#<id>`) | `installation_id-index` (hash `installation_id`), `ws_issue-link-index` (hash `ws_issue`, range `linked_at`) | none |

`idempotency` is already declared in M1 and carries the delivery ids under `ws#_platform#github-delivery#<X-GitHub-Delivery>` with its existing 24 hour TTL. No new table for that.

`project_config` gains the `project#<pid>#transition#<n>` sort key prefix design section 3 already reserved for it. No change to the table.

The `github` table carries a fourth sort-key prefix the design does not name, `webhook#<id>`, which is the decision recorded below.

Repository bundle:

- `integrations` writes `github`, `issues`, `activity`, `idempotency`, `project_config`, `rate-limits`; reads `memberships`, `workspaces`, `users`, `projects`, `comments`.

`integrations` writes `issues` because applying a transition is a status change, and it writes it through the same `IssueRepository` the issues domain uses rather than a second shape. That is the one place in the product where a domain writes another's table, and it is deliberate: the alternative is a synchronous call from a queue consumer into an authorized HTTP route, which would need a credential the consumer does not have and would put the gateway on the retry path.

## Where the webhook endpoint secret lives

No endpoint secret is stored. The row carries a random `secret_salt`, a salted SHA-256 `secret_hash` and the last four characters as `secret_hint`, and the secret itself is derived on demand from the per-environment `WEBHOOK_SIGNING_KEY` in the app secret:

```
secret = "whsec_" + HKDF-Expand(SHA256(WEBHOOK_SIGNING_KEY), "standupless.webhook.v1:<webhook_id>:<secret_salt>", 32)
```

The value shown once on create and once on rotate is that derived key itself, not an independent random string. That equality is the property to preserve: the dispatcher signs every delivery with the same derivation, so the value an admin pastes into their receiver is exactly the key that verifies what arrives. Minting an unrelated random secret and storing only its hash would hand the receiver a value that verifies nothing, because a hash cannot sign and the dispatcher would still have to sign with something else.

Rotation changes `secret_salt` alone, which changes the derived key, so a rotate genuinely invalidates the old secret. Deriving from the `webhook_id` alone would make a rotate rewrite the stored digest while the signing key stayed put, leaving a leaked secret working after somebody rotated it precisely because it leaked.

The cost is accepted deliberately: `WEBHOOK_SIGNING_KEY` is one key whose loss invalidates every endpoint in the environment, and it is held in the app secret rather than in any table. What it buys is that a read grant on the `github` table is not a read grant on any customer's signing key, since no customer secret is ever at rest there. The `secret_hash` is what a future "does this endpoint still hold the right secret" check reads, and `secret_hint` is what the settings page shows.

## Authorization rules

Every workspace-scoped route here depends on the M1 `require(...)` dependency and declares a capability that already exists. No new `Capability` member is added.

- Every `/github` and `/webhooks` route under a workspace declares `Capability.WORKSPACE_ADMIN`, which is the "Manage members, API keys, GitHub install" row of the design section 2 table. A member or a guest gets 403, and a non-member gets 404 on the workspace, indistinguishable from a workspace that does not exist.
- The transition routes declare `Capability.PROJECT_READ` for the list and `Capability.PROJECT_ADMIN` for the writes, with the project in the path, so a guest outside the project gets 404 and a project member who is not a project admin gets 403.
- `GET .../issues/{issue_id}/github-links` declares `Capability.WORKSPACE_READ` and then decides against the issue's own project with `can_see_project`, which is the same fail-closed shape M3's comment reads use, and the same indistinguishable 404.
- `GET /github/callback` and `POST /github/webhooks` carry no dependency at all. They are the two routes `tests/common/test_route_contract.py` now allows to be public, named individually in `PUBLIC_ROUTES` there, so the fixture diff still surfaces any third one.
- The consumers carry no user. They write what a request could have written and never call `require`, and a gateway request to `/events` is 404 by `register_stream_consumer`'s own guard.

## Error codes

Beyond the platform envelope's own `NOT_FOUND`, `FORBIDDEN`, `NOT_AUTHENTICATED`, `CONFLICT` and `VALIDATION_ERROR`:

| Code | Status | When |
|---|---|---|
| `NOT_FOUND` | 404 | The workspace, the installation, the webhook endpoint, the transition or the issue is absent, or the caller may not see the project it belongs to |
| `INVALID_SIGNATURE` | 401 | `X-Hub-Signature-256` is missing or does not verify against the webhook secret |
| `INVALID_STATE` | 400 | The callback's `state` is absent, malformed, expired or signed under another audience |
| `GITHUB_UNAVAILABLE` | 502 | The callback's installation or repository read did not answer |
| `CONFLICT` | 409 | A second installation is recorded for a workspace that already has one |
| `VALIDATION_ERROR` | 422 | A transition names a status outside the project, a webhook URL is not `https`, or `events` carries a name outside `OUTBOUND_EVENTS` |
| `NOT_CONFIGURED` | 503 | The App credentials are absent from the secret, so the install flow cannot run |

`NOT_CONFIGURED` is its own code because it is the state of every environment until the owner creates the App and fills the secret, and a frontend showing "GitHub is not set up in this environment" is a better answer than a 500.

## Pagination

Unchanged from M2 and M3 for the one list that can grow: `GET .../issues/{issue_id}/github-links` takes `cursor` and `limit` and answers `{"links": [...], "next_cursor": ...}`. The other three lists are bounded by construction, one installation, its repositories and a project's transition rules, and each answers its whole set with no cursor.

## Platform gaps

Verified against `webbpulse` 0.43.0 as installed and `terraform-aws-platform-modules` as pinned. Design section 6's `verify_hmac_signature`, `IdempotencyStore.claim`, `events.enqueue`, `events.webhooks`, `deserialize_image`, `source_table` and `identity.scopes` have all landed and are used here rather than reimplemented. What M5 still wants:

| Gap | Where | Proposed surface |
|---|---|---|
| A GitHub App client | `webbpulse-python` | Minting an installation token from an App private key is the same twenty lines in every product that installs a GitHub App: an RS256 App JWT, then `POST /app/installations/<id>/access_tokens`, then a cached token with an expiry. `webbpulse.integrations.github.installation_token(app_id, private_key, installation_id)` plus a thin `GitHubClient` belongs upstream. Built locally for now in `app/domains/integrations/github_api.py`. |
| Per-endpoint secret derivation | `webbpulse-python` | The HKDF derivation this contract uses for webhook signing keys is the same shape as the TOTP envelope key derivation already in the platform. `webbpulse.security.derive_key(master, info)` would close both. |
| SQS consumer entrypoint shape | `webbpulse-python` | `register_stream_consumer` handles an SQS batch and a DynamoDB stream batch alike, which is right, but a queue consumer wants the message body parsed back into an `EventEnvelope` and the shape is hand-rolled per consumer. `webbpulse.events.queue_records(event)` yielding `EventEnvelope` would close it. |
| Outbound webhook endpoint storage | `webbpulse-python` | Every product that offers outbound webhooks stores a URL, an event list, an active flag and a secret the same way. An `WebhookEndpointStore` protocol beside `events.webhooks` would let the dispatcher take endpoints rather than each product shaping them. |

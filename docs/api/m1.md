# M1 API contract: workspaces and teams

Fixed shape both halves build against. Routes are under `/api`. Every list body is an object with one plural key, never a bare array. Timestamps are ISO 8601 UTC. Ids are ULIDs unless noted. Errors use the platform envelope; a caller outside a workspace sees 404, never 403, for the workspace and anything inside it.

## Current user (`identity` domain)

| Method and path | Body in | Body out | Who |
|---|---|---|---|
| `GET /users/me` | none | `{"id", "email", "display_name", "email_verified", "email_notifications"}`; 404 when the token's row is gone | any signed in user |
| `PATCH /users/me/preferences` | `{"email_notifications"}` | the same body as `GET /users/me`; 404 when the token's row is gone | any signed in user, their own row only |
| `GET /users/me/deletion-plan` | none | `{"blocking", "deleted_with_account", "leaving"}`, each a list of `{"id", "name", "slug", "deletion_scheduled"}` | signed in user, no scoped token or key |
| `POST /users/me/deletion` | `{"confirm_email"}` | 204; 400 `CONFIRMATION_MISMATCH`; 409 `SOLE_OWNER` naming each blocking workspace; a repeat is 204 | signed in user after a step-up, no scoped token or key |

`email_notifications` is the one product preference on the `users` row. It defaults to true, so a row written before it existed reads as opted in. Turning it off stops notification email only: inbox rows are still written.

Deleting an account is immediate. A workspace where the caller is the only owner and other people remain blocks it, including one whose own deletion is scheduled, because that can still be cancelled. Once it passes, the row is marked deleted, every refresh family, OAuth grant (MCP clients included) and personal API key is revoked, every sign in method is refused with `ACCOUNT_DELETED`, a notice is emailed, and the purge is queued at once on the workspaces purge queue. The purge deletes the account's solo workspaces and memberships and then the row, which fires the identity purge of credentials; authored issues and comments stay and show as a deleted user. Until the row is gone, `/users/me`, the preferences route, creating a workspace and accepting an invite answer 401 `ACCOUNT_DELETED` to a token issued earlier. A failed send is retried by SQS and the hourly sweep purges any marked row it finds.

## Workspaces (`workspaces` domain)

| Method and path | Body in | Body out | Who |
|---|---|---|---|
| `GET /workspaces` | none | `{"workspaces": [Workspace]}` (every workspace the caller is a member of, from `memberships` `user_id-workspace_id-index`) | any signed in user |
| `POST /workspaces` | `{"name", "slug"}` | `Workspace`, 201; caller becomes `owner` | any signed in user |
| `GET /workspaces/{workspace_id}` | none | `Workspace` | member |
| `PATCH /workspaces/{workspace_id}` | `{"name"?}` | `Workspace` | owner, admin |
| `DELETE /workspaces/{workspace_id}` | none | 204 | owner |
| `GET /workspaces/{workspace_id}/members` | none | `{"members": [Member]}` | member |
| `PATCH /workspaces/{workspace_id}/members/{user_id}` | `{"role"}` | `Member` | owner, admin; only owner may grant or remove `owner` |
| `DELETE /workspaces/{workspace_id}/members/{user_id}` | none | 204; the last owner cannot be removed, and the person's team memberships go with them | owner, admin, or the user themself; only an owner removes another owner |
| `GET /workspaces/{workspace_id}/invites` | none | `{"invites": [Invite]}` | owner, admin |
| `POST /workspaces/{workspace_id}/invites` | `{"email", "role"}` (role never `owner`) | `Invite` plus `token` once, 201; the accept link is also emailed to `email` when this environment can reach it | owner, admin |
| `DELETE /workspaces/{workspace_id}/invites/{invite_id}` | none | 204 | owner, admin |
| `POST /invites/accept` | `{"token"}` | `Member`, 201; idempotent for an existing member; 403 `INVITE_EMAIL_MISMATCH` unless the caller's verified email is the invited one | the signed in user the invite was sent to |
| `GET /workspaces/{workspace_id}/auth-policy` | none | `AuthPolicy` | owner, admin, signed in session only |
| `PUT /workspaces/{workspace_id}/auth-policy` | `{"require_two_factor", "allowed_methods"}`, either may be left out to keep its stored value | `AuthPolicy`; turning two-factor on or taking a method out is 403 `PLAN_FEATURE_UNAVAILABLE` below Business; 409 `TWO_FACTOR_REQUIRED` when two-factor would be required and the caller's own session has no second factor; 409 `SIGN_IN_METHOD_REQUIRED` when the methods are restricted and leave out the one the caller's session signed in with; turning two-factor off or allowing a method again always succeeds | owner, admin, signed in session only |
| `GET /workspaces/{workspace_id}/approved-domains` | none | `{"domains": [ApprovedDomain]}` | owner, admin |
| `POST /workspaces/{workspace_id}/approved-domains` | `{"domain"}` | `ApprovedDomain`, 201; idempotent; 403 `DOMAIN_NOT_VERIFIED` unless it is the caller's own verified email domain, 422 `PUBLIC_EMAIL_DOMAIN` for public mail providers, 422 `INVALID_DOMAIN`, 409 `LIMIT_EXCEEDED` past 50 domains | owner, admin |
| `DELETE /workspaces/{workspace_id}/approved-domains/{domain}` | none | 204; members who joined through it stay | owner, admin |
| `GET /workspaces/joinable` | none | `{"workspaces": [JoinableWorkspace]}`: workspaces approving the caller's verified email domain that the caller is not in | any signed in user, signed in session only |
| `POST /workspaces/{workspace_id}/join` | none | `Member` with role `member`, 201, or 200 for an existing member; 404 unless the workspace approves the caller's verified email domain; 403 `PLAN_LIMIT_REACHED` at the member cap | any signed in user, signed in session only |
| `GET /workspaces/{workspace_id}/audit-log` | query `actor_id`, `event`, `since`, `until`, `limit` (1 to 100), `cursor` | `AuditLog`, newest first | owner, admin |
| `GET /workspaces/{workspace_id}/audit-log/export` | query `actor_id`, `event`, `since`, `until` | CSV attachment `audit-log.csv`, up to 5000 rows; 403 `PLAN_FEATURE_UNAVAILABLE` below Business | owner, admin |

`Workspace`: `id`, `name`, `slug` (lowercase, `[a-z0-9-]{3,40}`, unique through `slug-index`), `plan` (`"free"`), `created_at`, `role` (the caller's role, only present on responses to a member).
`Member`: `user_id`, `email`, `display_name`, `role`, `joined_at`.
`Invite`: `invite_id`, `email`, `role`, `invited_by`, `expires_at`, `created_at`.
`AuthPolicy`: `require_two_factor`, `allowed_methods` (some of `password`, `google`, `github`, `passkey`, in that order; all four when unrestricted), `updated_at`, `updated_by`, `available` (whether the plan includes it), `current_method` (how the caller's session signed in, or `null` when it cannot be told).
`ApprovedDomain`: `domain`, `added_by`, `added_at`.
`JoinableWorkspace`: `id`, `name`, `slug`, `icon_url`, `accent_color`, `domain` (the approved domain that admits the caller).
`AuditLog`: `events` (`[AuditEvent]`), `next_cursor`, `available` (whether the plan includes the audit log; below Business it is `false` with no events), `event_types` (`[{"key", "label"}]`).
`AuditEvent`: `audit_id`, `event`, `event_label`, `actor_id`, `actor_kind` (`user`, `api_key`, `service` or `system`), `actor_name`, `source` (`web`, `api`, `cli`, `mcp` or `system`), `ip`, `amr`, `target_type`, `target_id`, `target_label`, `before`, `after` (only the changed fields, never a secret), `created_at`.

Authentication policy. While `require_two_factor` is on, every route under the workspace answers 403 `AUTH_POLICY_REQUIRED` to a session whose person has no second factor, owners included, and `GET /workspaces` still lists the workspace with `auth_policy_blocked: true` so the client can explain why, with `auth_policy_reason` (`two_factor` or `sign_in_method`) and, for a refused method, `auth_policy_allowed_methods`. The session carries a `two_factor` claim, stamped by the identity hooks on every sign in and every refresh from the person's active TOTP factor or, while `passkeys_second_factor` is on, any registered passkey, because a password or OAuth sign in is then challenged for one. Enrolling takes effect on the next refresh and removing the last factor drops access the same way. A session whose `amr` shows `mfa` beside a real second factor (`otp`, `recovery` or `swk`) counts as well; `mfa` alone never does, because an OAuth sign in can carry it with no second factor. API keys and MCP tokens are delegated credentials and are not held to the claim, but MCP consent no longer offers a workspace whose policy the consenting session does not meet, checked against the session's `amr` through the package's `session_tenant_resolver`. The policy is a `policy#auth` row in `memberships`, which every function's authorization already reads. `GET /users/me` repeats the session's claim as `two_factor`, which the account page's authenticator app panel and the settings switch read. While `allowed_methods` leaves any method out, every route under the workspace also answers 403 `AUTH_POLICY_REQUIRED` with `reason: "sign_in_method"` and `allowed_methods` to a session that signed in another way; the method is checked before the second factor. The method is read from the session's `amr`: `oauth` followed by the provider gives `google` or `github`, a first factor of `swk` gives `passkey`, and `pwd` gives `password`; a session whose method cannot be told is refused while the methods are restricted. A passkey used as a second factor after a password leaves the method `password` and counts as two-factor. A stored row without `allowed_methods` allows every method. A step up keeps the sign-in `amr` and adds the step-up factor, and only `otp`, `recovery` or `swk` count as stepping up. API keys and MCP tokens are exempt from the method check as for two-factor. Changing either setting records an `auth_policy.updated` audit event, one per setting, with the old and new value.

Audit log. Member joins, removals, departures and role changes, invites sent and revoked, authentication policy changes, API keys created and revoked, connected apps authorized and revoked, exports and issue imports started, workspace settings changes, deletion scheduled and cancelled, plan changes, and teams created and deleted each write one row to the `audit` table, partitioned by workspace with a ULID sort key, so a date range is a key condition. Rows are written on every plan and age out a year later through the table's TTL; reading needs Business. Recording is best effort: a failed write is logged and never fails the change it describes. The workspace purge deletes the log. The MCP tool `list_audit_events` reads the same page.

### Plan limits

`plan` selects a row of `PLAN_LIMITS` in `app/common/plan_limits.py`, and `"free"` is the only plan. Each create takes its slot through a conditional counter in `app/common/plan_usage.py`, in the same transaction as its row; at the limit it answers 403 with `error_code` `PLAN_LIMIT_REACHED`, a sentence naming the number, and `details` `{"resource", "limit", "plan"}`. There is no billing, so the status is 403 rather than 402.

| Resource | Free limit | Checked on |
|---|---|---|
| `teams` | 50 live teams | `POST /workspaces/{workspace_id}/teams` |
| `members` | 250 workspace members | `POST .../invites` and `POST /invites/accept` |
| `invites` | 100 unexpired invites | `POST .../invites` |
| `webhooks` | 20, team scoped ones included | both webhook create routes |
| `api_keys` | 25 unrevoked keys | `POST .../api-keys` |

Issues are not limited: nothing holds a live issue count, and the per-team counter only grows.

## Teams (`teams` domain)

| Method and path | Body in | Body out | Who |
|---|---|---|---|
| `GET /workspaces/{workspace_id}/teams` | none | `{"teams": [Team]}` in the caller's saved order, unnamed teams after it oldest first; a guest sees only teams they are a member of | member |
| `PUT /workspaces/{workspace_id}/teams/order` | `{"team_ids": [id]}`, at most 500 | `{"teams": [Team]}` in the new order; saves the caller's own sidebar order on their workspace membership, keeping only teams they can see, once each; 403 for a caller with no membership row | member |
| `POST /workspaces/{workspace_id}/teams` | `{"name", "key_prefix", "description"?, "estimate_scale"?, "estimate_extended"?, "estimate_allow_zero"?, "estimate_count_unestimated"?}` | `Team`, 201; creator becomes team `admin`; default statuses seeded; 409 when the prefix is held or retired by any team | owner, admin, member |
| `GET /workspaces/{workspace_id}/teams/{team_id}` | none | `Team` | team reader |
| `PATCH /workspaces/{workspace_id}/teams/{team_id}` | `{"name"?, "key_prefix"?, "estimate_scale"?, "estimate_extended"?, "estimate_allow_zero"?, "estimate_count_unestimated"?, "description"?}` | `Team`; a new `key_prefix` retires the old one as an alias; 409 when another team holds or retired it, and then nothing in the patch is applied | team admin |
| `DELETE /workspaces/{workspace_id}/teams/{team_id}` | none | 204; idempotent, a repeat resumes a purge that stopped part way | workspace owner or admin |
| `POST .../teams/{team_id}/join` | none | `TeamMember`; the caller joins as `member`, or their existing membership comes back unchanged | team reader |
| `POST .../teams/{team_id}/leave` | none | 204; 404 when the caller holds no membership; 409 `LAST_TEAM_ADMIN` for the only admin | team reader |
| `GET .../teams/{team_id}/members` | none | `{"members": [TeamMember]}` | team reader |
| `PUT .../teams/{team_id}/members/{user_id}` | `{"role"}` | `TeamMember`; 409 `LAST_TEAM_ADMIN` when it would demote the only admin | team admin |
| `DELETE .../teams/{team_id}/members/{user_id}` | none | 204; 409 `LAST_TEAM_ADMIN` for the only admin | team admin |
| `GET .../teams/{team_id}/statuses` | none | `{"statuses": [Status]}` ordered by `position` | team reader |
| `POST .../teams/{team_id}/statuses` | `{"name", "category", "position"?}` | `Status`, 201 | team admin |
| `PATCH .../teams/{team_id}/statuses/{status_id}` | `{"name"?, "category"?, "position"?}` | `Status` | team admin |
| `DELETE .../teams/{team_id}/statuses/{status_id}` | none | 204; 409 when it is the last status of its category | team admin |
| `GET .../teams/{team_id}/labels` | none | `{"labels": [Label]}` | team reader |
| `POST .../teams/{team_id}/labels` | `{"name", "color"}` | `Label`, 201 | team admin |
| `PATCH .../teams/{team_id}/labels/{label_id}` | `{"name"?, "color"?}` | `Label` | team admin |
| `DELETE .../teams/{team_id}/labels/{label_id}` | none | 204 | team admin |

`Team`: `id`, `workspace_id`, `name`, `key_prefix` (uppercase `[A-Z][A-Z0-9]{1,5}`, unique per workspace through `workspace_key_prefix-index`), `description` (nullable), `estimate_scale` (`"off" | "exponential" | "fibonacci" | "linear" | "tshirt"`, default `"off"`), `estimate_extended` (adds the larger values: exponential 32 and 64, fibonacci 13 and 21, linear 6 and 7, tshirt XXL and XXXL; default false, and true for a fibonacci or linear team stored before the toggle existed), `estimate_allow_zero` (adds `0`, default false), `estimate_count_unestimated` (cycle and project progress count an unestimated issue as 1 point instead of skipping it, default false), `next_issue_number` is never exposed, `created_at`, `updated_at`, `role` (the caller's team role: `admin` or `member`, or the workspace role's implied `admin` for owner and admin, `member` for member), `member_count` (explicit team memberships), `is_member` (whether the caller holds one), `retired_key_prefixes` (filled on the single team routes, empty on the list).

Key changes. A retired prefix is kept as an alias row in `teams` (`team_id = alias#<KEY>`, carrying the same `workspace_key_prefix`), so the uniqueness index keeps it unavailable to every other team and `GET .../issues/by-key/OLD-12` still resolves. Issue rows keep their team id and number and are never rewritten. A team may take back a prefix it retired. The `key` stored on an issue row is the key at creation time; issue reads still return that stored value.

Join and leave. An open team is open to workspace owners, admins and members, who may join or leave it themselves. Guests stay invite only, reaching just the teams a team admin added them to. A team keeps at least one explicit admin.

Private teams. `private` on `Team` (settable on create and `PATCH`; turning it on needs the Business plan, turning it off never does, and a downgrade keeps existing private teams private). A private team is invite only: to anyone not on it every team route, issue, search hit, view, cycle and project scoped to it answers as if it did not exist, and self join is refused. Workspace owners and admins still see it in the team list and settings and may administer it or add themselves, but read none of its content until they do. The marker is a `private_team#<team_id>` row in `memberships`, so every bundle can read it without another table. Public share links stop resolving once their creator leaves the workspace, and a link into a private team, or one minted by a guest, also stops once its creator is no longer on that team, workspace wide webhooks skip events whose teams are all private (team scoped webhooks still receive them), and notifications go only to people who can see the team.

Delete. The team row is tombstoned first (`deleting_at`), which hides it from every read and frees its prefix, then its memberships, statuses, labels, transitions, issue counter and alias rows are purged a page at a time. The rows other domains own are then handed to the team purge chain, one SQS queue per domain: discussion (comments, reactions, attachments and their stored files), integrations (GitHub links, repository pins), views (team views, search rows, share links), planning (cycles; the team leaves each project's `team_ids`, and a project left with no team is deleted), issues (issues, relations, activity), and finally teams, which removes the tombstoned row. Every stage checks the tombstone first, works a page at a time within a time budget and resumes from a cursor, and a failed message lands in its queue's dead-letter queue. A repeat DELETE on a team still deleting starts the chain again. Where the queues are not configured the tombstone stays.
`TeamMember`: `user_id`, `email`, `display_name`, `role` (`admin` or `member`), `added_at`.
`Status`: `id`, `name`, `category` (`backlog | unstarted | started | completed | cancelled`), `position` (integer, ascending). Default seed on create: Backlog (backlog, 0), Todo (unstarted, 1), In Progress (started, 2), Done (completed, 3), Cancelled (cancelled, 4).
`Label`: `id`, `name`, `color` (`#rrggbb`).

"Team reader" is any workspace owner, admin or member, or a guest holding a team membership. "Team admin" is a workspace owner or admin, or a team member with role `admin`.

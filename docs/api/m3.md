# M3 API contract: discussion and views

Fixed shape both halves build against, in the M1 and M2 style: routes under `/api`, list bodies are objects with one plural key beside `next_cursor`, timestamps ISO 8601 UTC, ids ULIDs, platform error envelope, and a caller outside a workspace sees 404 never 403. Two domains land here, `discussion` and `views`, plus the two stream consumers `views` owns.

Everything is workspace scoped and reached through the M1 authorization dependency at `app/common/api/dependencies/authz.py`. No route here introduces a second way to decide access: a comment, a reaction, an attachment and a board column are all readable exactly when the issue's team is readable, and writable exactly when the caller is a team member. There is no new capability and no new role.

Route prefixes for the gateway, matching `lambda_domain_path_prefixes` in `terraform/apigateway.tf`:

| Domain | Prefix |
|---|---|
| `discussion` | `/api/workspaces/{workspace_id}/issues/{issue_id}/comments`, `/api/workspaces/{workspace_id}/comments`, `/api/workspaces/{workspace_id}/reactions`, `/api/workspaces/{workspace_id}/attachments` |
| `views` | `/api/workspaces/{workspace_id}/views`, `/api/workspaces/{workspace_id}/board`, `/api/workspaces/{workspace_id}/search`, `/api/workspaces/{workspace_id}/inbox` |

Two prefixes route to `discussion` under the `issues` prefix's own subtree, so the gateway needs the comment prefix declared ahead of `issues` on specificity, not on order: API Gateway HTTP API picks the most specific match, and `/api/workspaces/{workspace_id}/issues/{issue_id}/comments/{proxy+}` is more specific than `/api/workspaces/{workspace_id}/issues/{proxy+}`. The `discussion` domain does not otherwise serve anything under `/issues`.

Design section 1 lists the prefixes as `/api/comments`, `/api/reactions`, `/api/attachments`, `/api/views`, `/api/search`, `/api/inbox`. Those are the unscoped forms; as with M1 and M2 every one is nested under `/api/workspaces/{workspace_id}` so the tenant is in the path and the dependency reads it from there rather than from a body or a header. `/api/share-links` and `/api/shared` stay out of M3 and land with M6.

## Routes (`discussion` domain)

### Comments

| Method and path | Body in | Body out | Who |
|---|---|---|---|
| `GET /workspaces/{workspace_id}/issues/{issue_id}/comments` | query `cursor?`, `limit?` (1 to 100, default 50) | `{"comments": [Comment], "next_cursor": string or null}` oldest first, a thread read in order | team reader |
| `POST /workspaces/{workspace_id}/issues/{issue_id}/comments` | `{"body", "parent_comment_id"?, "attachment_ids"?}` | `Comment`, 201; `body` may be blank only when `attachment_ids` is not empty; every attachment id must name an attachment on this issue (422 otherwise, at most 10); mentions extracted and one `inbox` row per mentioned member arrives asynchronously | team member |
| `GET /workspaces/{workspace_id}/comments/{comment_id}` | query `issue_id` (required) | `Comment` | team reader |
| `PATCH /workspaces/{workspace_id}/comments/{comment_id}` | `{"issue_id", "body"}` | `Comment` with `edited_at` set | the author only |
| `DELETE /workspaces/{workspace_id}/comments/{comment_id}` | query `issue_id` (required) | 204; the row is removed, replies are reparented to null, reactions on it are removed | the author, or a team admin |

`issue_id` is required on the single-comment routes because the `comments` table partitions by `ws_issue`; without it the read would be a scan, which design section 2 forbids outside an admin path. It is a query parameter rather than a path segment so a comment id stays stable in a permalink built from the issue route.

### Reactions

| Method and path | Body in | Body out | Who |
|---|---|---|---|
| `GET /workspaces/{workspace_id}/reactions` | query `target_id` (required, an issue id or a comment id), `target_kind` (`issue` or `comment`) | `{"reactions": [ReactionGroup]}` | team reader |
| `PUT /workspaces/{workspace_id}/reactions` | `{"target_id", "target_kind", "emoji"}` | `ReactionGroup` for that emoji, 200; idempotent, a second PUT by the same user is the same answer | team member |
| `DELETE /workspaces/{workspace_id}/reactions` | query `target_id`, `target_kind`, `emoji` | 204; removing a reaction that is not there is still 204 | the reacting user only |

A reaction is a `PUT` and a `DELETE` on the pair rather than a create and a delete by id, because the row's own key is `<emoji>#<user_id>`: the caller already knows the key, and there is no id to hand back. Comment reads carry their reaction groups inline so a thread does not need one call per comment.

### Attachments

| Method and path | Body in | Body out | Who |
|---|---|---|---|
| `GET /workspaces/{workspace_id}/attachments` | query `issue_id` (required), `cursor?`, `limit?` | `{"attachments": [Attachment], "next_cursor"}` oldest first | team reader |
| `POST /workspaces/{workspace_id}/attachments/url` | `{"issue_id", "url", "title"?}` | `Attachment` with `kind` `"url"`, 201 | team member |
| `POST /workspaces/{workspace_id}/attachments/uploads` | `{"issue_id", "filename", "content_type", "size_bytes"}` | `UploadTicket`, 201; nothing is stored on the issue yet | team member |
| `POST /workspaces/{workspace_id}/attachments` | `{"issue_id", "upload_id", "title"?}` | `Attachment` with `kind` `"file"`, 201; 409 when the object is not in the bucket, 404 when the ticket is unknown or not the caller's | team member |
| `GET /workspaces/{workspace_id}/attachments/{attachment_id}/download` | query `issue_id` (required) | `{"url", "expires_at"}`, a presigned GET valid for 300 seconds | team reader |
| `DELETE /workspaces/{workspace_id}/attachments/{attachment_id}` | query `issue_id` (required) | 204; the row goes immediately, the S3 object is left to the bucket lifecycle rule | the uploader, or a team admin |

The upload is three calls on purpose. `POST .../uploads` mints a presigned PUT through `webbpulse.storage.presigned_put(bucket, key, content_type, max_bytes)`, which signs the `Content-Type` and the `Content-Length` into the URL, so the ceiling is enforced by S3 at the header rather than measured after the bytes land. The browser PUTs straight to S3 with exactly the headers the ticket names. The third call records the attachment, and only that call makes it visible on the issue, so an abandoned upload is an orphaned object the lifecycle rule collects and never a half-attached row.

The object key is `workspaces/{workspace_id}/issues/{issue_id}/{upload_id}/{filename}`. The workspace id is the first segment so an IAM condition or a bucket policy can be written per tenant later without a migration. `upload_id` is a ULID minted server side; a client never names a key.

`max_bytes` is `size_bytes` from the request, capped at 25 MiB. A larger `size_bytes` is 422 rather than a silently smaller ceiling, because a client that declares 100 MB and gets a 25 MiB URL fails at the end of the upload rather than at the start.

Downloads are presigned GETs through `webbpulse.storage.presigned_get(bucket, key, expires_in, response_content_disposition=...)`, minted per request, never stored and never logged. The bucket stays private and blocks all public access; bytes never pass through a Lambda. `response_content_disposition` carries the original filename so a stored ULID key downloads under a human name, and it is `attachment` rather than `inline` for every type outside the inline-safe set, so a stored `text/html` cannot be served as a page from the bucket origin.

Accepted `content_type` values on an upload are an allow list: `image/png`, `image/jpeg`, `image/gif`, `image/webp`, `image/svg+xml` is refused, `application/pdf`, `text/plain`, `text/csv`, `application/zip`, and the two office bundles. Anything else is 422. An image is `inline` on download, everything else is `attachment`.

A URL attachment stores `url`, `title` and `favicon_url` derived as `https://www.google.com/s2/favicons?domain=<host>` without a fetch; the MVP does not crawl the target, so a title the caller does not give defaults to the host.

## Routes (`views` domain)

### Board

| Method and path | Body in | Body out | Who |
|---|---|---|---|
| `GET /workspaces/{workspace_id}/board` | query `team_id` (required), `assignee_id?` (`me` allowed), `label_id?`, `priority?`, `cycle_id?`, `project_id?`, `column_limit?` (1 to 100, default 50) | `Board` | team reader |
| `GET /workspaces/{workspace_id}/board/columns/{status_id}` | query `team_id` (required), the same filters, `cursor?`, `limit?` | `{"issues": [Issue], "next_cursor"}` | team reader |

The board read is one call per team, not per column: it reads the team's statuses from `team_config` and queries `issues` on `ws_team-status_updated-index` once per status, each capped at `column_limit`, and returns every column with its own `next_cursor`. A column deeper than its cap is paged through the column route rather than by raising `column_limit`, which is what keeps one request's fan-out bounded by the number of statuses.

Dragging a card is not a board route. It is `PATCH /api/workspaces/{workspace_id}/issues/{issue_id}` with `status_id`, already in the M2 contract, so there is exactly one write path onto an issue and one place activity is written.

### Saved views

| Method and path | Body in | Body out | Who |
|---|---|---|---|
| `GET /workspaces/{workspace_id}/views` | query `scope?` (`mine` default, `team`, `all`), `team_id?` | `{"views": [SavedView]}` | member; a guest sees only their own views and team views for teams they are in |
| `POST /workspaces/{workspace_id}/views` | `{"name", "kind", "filter", "sort"?, "group_by"?, "sub_group_by"?, "ordering"?, "visible_properties"?, "layout"?, "team_id"?}` | `SavedView`, 201 | team member when `team_id` is set, otherwise any member for a personal view |
| `GET /workspaces/{workspace_id}/views/{view_id}` | none | `SavedView` | the owner for a personal view, team reader for a team view |
| `PATCH /workspaces/{workspace_id}/views/{view_id}` | any of `name`, `filter`, `sort`, `group_by`, `sub_group_by`, `ordering`, `visible_properties`, `layout` | `SavedView` | the owner, or a team admin for a team view |
| `DELETE /workspaces/{workspace_id}/views/{view_id}` | none | 204 | the owner, or a team admin for a team view |

A saved view stores a filter, it does not store results. Running one is the M2 issue list with the stored filter applied, which the frontend does by expanding `filter` into the `GET /issues` query. There is deliberately no `GET /views/{view_id}/issues`: a second read path would be a second place team visibility is decided, and the invariant in design section 2 is that there is one.

`filter` is validated on write against the same field set the issue list accepts: `team_id`, `status_id`, `status_category`, `assignee_id`, `label_id`, `priority`, `parent_id`, `cycle_id`, `project_id`, `due_before`, `due_after`, `q`, and the negations `status_id_not`, `status_category_not`, `assignee_id_not`, `label_id_not`, `priority_not`, `cycle_id_not`, `project_id_not`. The repeatable keys take a string or a list of strings, a list meaning "any of"; `team_id`, `due_before`, `due_after` and `q` take one string. An unknown key or a malformed value is 422 rather than ignored, so a view cannot silently widen when a field is renamed, and every stored filter expands into a valid list query as repeated keys.

### Search

| Method and path | Body in | Body out | Who |
|---|---|---|---|
| `GET /workspaces/{workspace_id}/search` | query `q` (required, 2 to 128 chars), `team_id?`, `limit?` (1 to 50, default 20) | `{"results": [SearchResult]}` ranked, no cursor | member |

Search reads the `search_index` projection the `views-search-consumer` maintains. The query is lowercased and split the same way the indexer splits, terms of three characters or fewer are dropped, and each surviving term is one query on `ws_team` with `term_doc` beginning with `<term>#`. Results are the intersection of the per-term posting sets, ranked by how many terms matched and then by `updated_at` descending.

Scope is fail-closed: without `team_id` the fan-out is over exactly the teams the caller can see, which for a guest is `AuthzContext.team_ids` and for everyone else is the workspace's teams. There is no cross-workspace read by construction, because `ws_team` begins with the workspace id.

A key lookup short-circuits: when `q` matches `^[A-Za-z][A-Za-z0-9]{1,5}-\d+$` the answer is the single issue from `ws_team-key_number-index`, no index read. That is what makes typing `ABC-123` exact rather than a relevance guess.

Search is not paged. The MVP caps at `limit` results and says so; a cursor over an intersection of posting lists is a post-MVP decision alongside the OpenSearch one in design section 3.

### Inbox

| Method and path | Body in | Body out | Who |
|---|---|---|---|
| `GET /workspaces/{workspace_id}/inbox` | query `unread?` (bool, default false), `cursor?`, `limit?` (1 to 100, default 50) | `{"notifications": [Notification], "next_cursor"}` newest first | any member, their own rows only |
| `GET /workspaces/{workspace_id}/inbox/count` | none | `{"unread": integer}` counted from the sparse index, capped and reported as `100` above 100 | any member |
| `POST /workspaces/{workspace_id}/inbox/read` | `{"notification_ids"}` (1 to 100 ids) or `{"all": true}` | `{"updated": integer}` | any member, their own rows only |
| `DELETE /workspaces/{workspace_id}/inbox/{notification_id}` | none | 204 | any member, their own rows only |

The inbox is per user by construction: the partition key is `<workspace_id>#<user_id>` built from `AuthzContext`, never from a parameter, so there is no route by which one member reads another's inbox and no id to guess. `unread=true` reads `ws_user-unread-index`, which is sparse and holds only unread rows, so the badge is a short index query rather than a filtered scan.

Marking read deletes the `unread_at` attribute, which removes the row from the sparse index in the same write. A notification whose issue or comment has since been deleted still renders, carrying the denormalised title it was written with, rather than 404ing a list.

### Consumers

| Method and path | Body in | Body out | Who |
|---|---|---|---|
| `POST /events` on `views-notify-consumer` | stream records | consumer only; a gateway request 404s | none |
| `POST /events` on `views-search-consumer` | stream records | consumer only; a gateway request 404s | none |

Both mount through `webbpulse.events.register_stream_consumer`, which already guards the gateway case and returns the `ReportBatchItemFailures` envelope, exactly as the M2 rollup consumer does. Both run the `views` image under a different entrypoint, `app.domains.views.consumers.notify_entrypoint` and `app.domains.views.consumers.search_entrypoint`.

## Shapes

`Comment`: `comment_id` (ULID, so the table's own sort order is chronological), `issue_id`, `workspace_id`, `team_id` (denormalised, so a reader can decide visibility without a second read), `body` (markdown, up to 65536 bytes, empty only on a comment that carries attachments), `parent_comment_id` (nullable, one level deep: a reply cannot itself be replied to), `author_id`, `author` (`{user_id, display_name, email}`), `mentions` (list of user ids, extracted on write by `webbpulse.messages.extract_mentions`), `reactions` (list of `ReactionGroup`), `reply_count` (integer, direct replies only), `attachments` (list of `Attachment`, the ones named by `attachment_ids` on create, in that order; one removed since drops out rather than 404ing the comment), `created_at`, `edited_at` (nullable), `deleted` is not a field: a delete removes the row.

`ReactionGroup`: `emoji` (a single Unicode emoji, at most 8 code points, validated against a fixed allow list of 24), `count`, `user_ids` (capped at the first 20, in key order), `reacted` (whether the caller is one of them). A group with `count` zero is never returned.

`Attachment`: `attachment_id` (ULID), `issue_id`, `workspace_id`, `team_id`, `kind` (`"url" | "file"`), `title` (1 to 200 chars), `url` (present when `kind` is `"url"`, `https` only, at most 2048 chars), `favicon_url` (nullable, `kind` `"url"` only), `s3_key` and `content_type` and `size_bytes` (present when `kind` is `"file"`; `s3_key` is returned so the frontend can key a cache, and it is not a credential), `uploaded_by`, `created_at`. A `file` attachment never carries a URL in its stored row: the only way to a byte is the download route, which mints one per request.

`UploadTicket`: `upload_id` (ULID), `url` (the presigned PUT), `headers` (the exact headers the PUT must send, straight from `PresignedUpload.headers`, none of them advisory), `s3_key`, `max_bytes`, `expires_at`. The ticket is written to `idempotency` under `upload#<workspace_id>#<upload_id>` with a 24 hour TTL carrying `issue_id`, `s3_key`, `content_type`, `size_bytes` and the minting user, so the commit call verifies the key it is handed was minted for this caller on this issue rather than trusting a key from the body.

`Board`: `team_id`, `columns` (list of `BoardColumn` in `position` order). `BoardColumn`: `status_id`, `name`, `category`, `position`, `issues` (list of `Issue`, the M2 shape unchanged), `total` (the column's count, exact up to 1000 and reported as `1000` above it), `next_cursor`.

`SavedView`: `view_id` (ULID), `workspace_id`, `name` (1 to 80 chars), `kind` (`"list" | "board"`), `scope` (`"personal" | "team"`, derived from whether `team_id` is set, never sent), `team_id` (nullable), `filter` (object, see above), `sort` (one of the M2 issue list sorts, default `updated_desc`), `group_by` (nullable, `"status" | "assignee" | "priority" | "label"`), `sub_group_by` (nullable, the same values, needs a `group_by` and must differ from it), `ordering` (nullable display order within groups, the `sort` vocabulary; null follows `sort`), `visible_properties` (nullable list of `id`, `status`, `priority`, `assignee`, `labels`, `estimate`, `start_date`, `due_date`, `project`, `cycle`, `parent`, `sub_issues`, `created_at`, `updated_at`, repeats collapsed; null means the client default), `layout` (`"list" | "board"`, defaulting to `kind` when unset; `kind` stays the fixed type, `layout` the patchable display), `owner_id`, `created_at`, `updated_at`.

`SearchResult`: `issue_id`, `key`, `title`, `team_id`, `status_id`, `assignee_id`, `updated_at`, `score` (integer, matched term count). No snippet: the index stores terms, not positions, so a snippet would need the issue body read per result.

`Notification`: `notification_id` (ULID), `workspace_id`, `kind` (`"assigned" | "mentioned" | "commented" | "status_changed" | "reacted"` is not in the MVP), `issue_id`, `issue_key`, `issue_title` (denormalised at write), `team_id`, `comment_id` (nullable), `actor_id`, `actor_name`, `unread` (derived from whether `unread_at` is set), `created_at`, `expires_at` (90 days out).

## Consumer event contracts

### `views-notify-consumer`

Sources: the `issues` table stream and the `comments` table stream, both `NEW_AND_OLD_IMAGES`, both mapped to the same function.

Filter pattern: `{"eventName": ["INSERT", "MODIFY"]}`. A `REMOVE` produces no notification, so it is filtered at the mapping and never billed as an invocation.

Both images are read with `webbpulse.events.deserialize_image(record, "NewImage")` and `"OldImage"`. The source table is told apart by `eventSourceARN` rather than by guessing from the attributes present, because a filtered record carries no marker of its own.

What it writes:

- An `issues` INSERT with a non-null `assignee_id` writes one `assigned` row for the assignee.
- An `issues` MODIFY where `assignee_id` changed to a non-null value writes one `assigned` row for the new assignee. The old assignee is not notified.
- An `issues` MODIFY where `status_id` changed writes one `status_changed` row for the assignee, when there is one and it is not the actor.
- A `comments` INSERT writes one `commented` row for the issue's assignee and for the author of every ancestor comment in the thread, and one `mentioned` row for each id in the record's `mentions`. A member who would get both gets only `mentioned`, which is the stronger signal.
- Nothing is ever written for the actor themself. `actor_id` comes from `created_by` or `updated_by` on the image; the row is skipped when it equals the recipient.

Every recipient is filtered through team visibility before the row is written: the consumer reads the workspace membership, and for a guest reads the team membership, so a guest who is no longer in a team stops receiving its notifications without anything being cleaned up. A recipient with no membership is dropped silently.

Idempotency: the notification id is not a fresh ULID. It is `ULID(created_at) + hash(kind, recipient, source_id)` truncated, computed from the record, so a redelivered record writes the same key and the put is conditional on absence. A redelivery is a no-op rather than a duplicate row, which is what makes the consumer safe under the partial-batch retry the event source mapping performs.

Failures raise per record, so only that record enters `batchItemFailures`.

Email: every row the conditional put actually writes is also sent as one email to the recipient's account address through SES, so a redelivered record that writes no row sends no second message. The inbox stays primary and the email is best effort. No send happens when the recipient has `email_notifications` off, when the user row is disabled, or when the address is not on `EMAIL_VERIFIED_RECIPIENTS` (fed from the `ses_verified_recipients` terraform variable while the account is in the SES sandbox; empty means unrestricted). A refusal from SES is logged and swallowed. None of these fails the record, so none of them costs the shard a retry. Besides `identity` (verification and reset mail), only this function and `workspaces` (invite mail) hold `ses:SendEmail`.

### `views-search-consumer`

Source: the `issues` table stream, `NEW_AND_OLD_IMAGES`.

Filter pattern: `{"eventName": ["INSERT", "MODIFY", "REMOVE"]}`. A REMOVE has to be handled, otherwise a deleted issue stays findable.

What it writes: for each record it computes the term set of the new image from `key`, `title` and the first 4096 bytes of `body`, lowercased, split on non-alphanumerics, terms of three characters or fewer dropped, and the same for the old image. It writes the terms that appeared and deletes the terms that went away, both on `search_index` under `ws_team` equal to `<workspace_id>#<team_id>` and `term_doc` equal to `<term>#<issue_id>`. A REMOVE deletes every term of the old image.

An issue that moves between teams is not a case: `team_id` is never changeable per the M2 contract.

Postings per term per team are capped at 5000. Past the cap the write is skipped and the term is recorded in a `truncated` attribute on a marker row, so a hot term degrades a result set rather than a partition.

Idempotency: writing a term is a `put` of a row whose whole content is its key, and deleting one is a delete that tolerates absence, so replaying a record converges on the same state. Nothing is incremented.

Failures raise per record.

## Tables this project adds

Same notation as M2, per `docs/design.md` section 3.

| Table | PK | SK | GSIs | TTL / stream |
|---|---|---|---|---|
| `comments` | `ws_issue` (`<workspace_id>#<issue_id>`) | `comment_id` (ULID) | `ws_author-created_at-index` (hash `ws_author` = `<workspace_id>#<author_id>`, range `created_at`) | stream `NEW_AND_OLD_IMAGES` |
| `reactions` | `ws_target` (`<workspace_id>#<target_id>`) | `reaction_key` (`<emoji>#<user_id>`) | none | none |
| `attachments` | `ws_issue` (`<workspace_id>#<issue_id>`) | `attachment_id` (ULID) | none | none |
| `views` | `workspace_id` | `view_key` (`user#<uid>#view#<vid>` or `team#<pid>#view#<vid>`) | none | none |
| `inbox` | `ws_user` (`<workspace_id>#<user_id>`) | `notification_id` (ULID) | `ws_user-unread-index` (hash `ws_user`, range `unread_at`), sparse: `unread_at` is written only while unread and deleted on read | TTL `expires_at`, 90 days |
| `search_index` | `ws_team` (`<workspace_id>#<team_id>`) | `term_doc` (`<term>#<issue_id>`) | none | none, stream maintained |

`idempotency` is already declared in M1 and carries the upload tickets under `upload#<workspace_id>#<upload_id>` with its existing 24 hour TTL. No new table for that.

The `issues` table gains no change: its `NEW_AND_OLD_IMAGES` stream from M2 now feeds three mappings, the M2 rollup on the `issues` function plus the two `views` consumers. A DynamoDB stream supports two consumers per shard comfortably and up to five, so three mappings is inside the limit with room; a fourth would want a fan-out through EventBridge Pipes rather than a fourth direct reader, which is a post-MVP note not an M3 change.

Repository bundles:

- `discussion` writes `comments`, `reactions`, `attachments`, `idempotency`, `rate-limits`; reads `memberships`, `workspaces`, `users`, `teams`, `issues`.
- `views` writes `views`, `inbox`, `search_index`, `rate-limits`; reads `memberships`, `workspaces`, `users`, `teams`, `team_config`, `issues`, `comments`.

`views` reads `issues` and never writes it, which is what keeps the board and the search projection from becoming a second write path onto an issue. The consumers run in the same image and so carry the same bundle, which is why `inbox` and `search_index` are writes on the domain rather than on a separate function.

## Authorization rules

Every route here depends on the M1 `require(...)` dependency and declares one of the capabilities that already exist. No new `Capability` member is added.

- Comment, reaction and attachment reads declare `Capability.TEAM_READ`. The team is not in the path, so the route reads the issue first and checks `AuthzContext.can_see_team(issue.team_id)`, which is a 404 when it is false. That is the same fail-closed shape M2 uses for an issue read and the same indistinguishable 404.
- Comment, reaction and attachment writes need the caller to be a team member: workspace `owner`, `admin` or `member`, or a guest holding a membership in that issue's team. A guest outside the team gets 404, never 403.
- Editing a comment is the author alone, not a team admin. Deleting is the author or a team admin, which is `AuthzContext.is_team_admin` resolved against the issue's team.
- Removing a reaction is the reacting user alone. There is no moderation path in the MVP.
- Deleting an attachment is the uploader or a team admin.
- The board and the search fan-out enumerate visible teams from `AuthzContext`: `team_ids` for a guest, the workspace's teams otherwise. A `team_id` a guest cannot see is 404 on the board, not an empty board.
- Saved views: a personal view is the owner's alone, and `owner_id` comes from `AuthzContext.user_id`, never from a body. A team view is readable by any team reader and writable by the owner or a team admin.
- The inbox is the caller's own rows only, and the partition key is built from the context, so there is no cross-user read to authorize.
- The consumers carry no user. They read memberships directly to decide a recipient and write nothing a request could not have written. They never call `require`, and a gateway request to `/events` is 404 by `register_stream_consumer`'s own guard.

The route-contract fixture and the per-domain route counts are regenerated with this project, per the invariant in design section 2, so the diff on that fixture is the review artifact for whether a route here became public.

## Error codes

Beyond the platform envelope's own `NOT_FOUND`, `FORBIDDEN`, `NOT_AUTHENTICATED`, `CONFLICT` and `VALIDATION_ERROR`:

| Code | Status | When |
|---|---|---|
| `NOT_FOUND` | 404 | The workspace, the issue, the comment, the attachment or the view is absent, or the caller may not see the team it belongs to |
| `FORBIDDEN` | 403 | The caller is in the team but is not the author, the uploader, the reacting user or a team admin |
| `CONFLICT` | 409 | A comment reply nests more than one level; an attachment commit names an object that is not in the bucket |
| `UNSUPPORTED_MEDIA_TYPE` | 422 | The upload's `content_type` is outside the allow list |
| `UPLOAD_TOO_LARGE` | 422 | `size_bytes` is above 25 MiB |
| `UNKNOWN_UPLOAD` | 404 | The `upload_id` on a commit has no ticket, its ticket expired, or it was minted for another caller or another issue |
| `INVALID_FILTER` | 422 | A saved view's `filter` carries a key outside the accepted set, or a value of the wrong shape for its key |
| `QUERY_TOO_SHORT` | 422 | Every term of a search query was three characters or fewer |

## Pagination

Unchanged from M2: an opaque base64url cursor over `LastEvaluatedKey`, minted and read by `app/common/api/pagination.py`, carrying the scope it was issued under so a cursor from one query is refused on another. Every list body is `{"<plural>": [...], "next_cursor": string or null}`, and `next_cursor` is null exactly when the set is exhausted.

Board columns each carry their own cursor, which is a cursor on the column route rather than on the board route: handing the board a cursor would have to mean one per column, and a single opaque string covering several independent index positions is a cursor nothing can page correctly.

Search returns no cursor at all, for the reason above.

## Platform gaps

Verified against `webbpulse` 0.41.0 as installed, `terraform-aws-platform-modules` at v2.24.0, and the `webbpulse-python` main branch. Most of design section 6 has already landed: `presigned_put`, `IdempotencyStore.claim`, `Repository.increment`, `deserialize_image`, `register_stream_consumer`, `CursorPage`, `new_ulid`, `extract_mentions`, `verify_hmac_signature`, `encode_cursor` and `decode_cursor`, `events.enqueue`, `events/webhooks`, and both `sqs_event_sources` and `dynamodb_stream_event_sources` on the `lambda-function` module. What M3 still needs:

| Gap | Where | Proposed surface |
|---|---|---|
| `webbpulse.storage.presigned_get` is not in a release | `webbpulse-python` | The function is on main, unreleased. Cut 0.42.0 before the M3 build starts; the attachment download route is the only reader and cannot be written against 0.41.0. |
| S3 bucket and object delete | `webbpulse-python` | `storage` presigns and nothing else. An attachment delete leaves the object, which the contract accepts by leaning on a lifecycle rule, but a `delete_object` helper beside the presigners would let the row delete and the object delete be one decision. Low priority, the lifecycle rule is a correct answer for the MVP. |
| Content type allow list | `webbpulse-python` | Every product that takes an upload rewrites the same allow list and the same inline versus attachment decision. `webbpulse.storage.UPLOAD_CONTENT_TYPES` plus `disposition_for(content_type)` belongs beside `presigned_put`, not in the product. |
| List envelope with one plural key | `webbpulse-python` | `http.CursorPage` renders items under `items`, and every list body in this product is an object with one plural key, so `app/common/api/pagination.py` exists as a product-local workaround already noted in M2. A `CursorPage` that takes its item key, or a factory producing the model, would remove it. |
| Sparse index maintenance | `webbpulse-python` | Marking read has to delete an attribute to leave a sparse index, which is a `REMOVE unread_at` update expression hand-written in the product. `Repository.remove_attributes(key, names)` beside the existing `set_attributes` closes it. |
| Stream source discrimination | `webbpulse-python` | `views-notify-consumer` reads two tables' streams on one route and tells them apart by parsing `eventSourceARN`. `webbpulse.events.source_table(record)` returning the table name is four lines and belongs upstream rather than in every multi-source consumer. |
| S3 bucket for attachments | `terraform-aws-platform-modules` | The `s3-bucket` module covers this: private, TLS-only policy, `cors_rules` for the browser PUT, `lifecycle_rules` for the orphan sweep. No module change needed. Confirmed on v2.24.0. |
| Two mappings onto one stream | `terraform-aws-platform-modules` | `dynamodb_stream_event_sources` is a map keyed per entry on one function, so two functions reading one stream is two module calls, which already works. But M3 wants the `views` image deployed as two extra functions with no gateway routes, and `lambda-function` has no notion of a function that is a consumer only. Nothing blocks it, the product declares three `lambda_domain` entries for one image; worth noting so the orchestrator does not expect a `consumers` argument. |
| `http-api` version pin | `Standupless` | `terraform/apigateway.tf` pins `~> 2.25` while the newest published tag is v2.24.0. Not an M3 gap on its own, but M3's apply will fail on the same constraint the current root already carries. Resolve before the build. |

The `http-api` module takes route keys verbatim, so this works, but nothing in the module holds that the more specific integration is declared. A test or a validation over overlapping proxy prefixes would catch the day one of them is dropped and every comment request silently starts landing on the issues function. |
| Frontend polling client | `webbpulse-typescript` | `@webbpulse/api-client` `usePolledQuery` with refetch-on-focus, from design section 6, is still open and M3 is the first project with a surface that visibly goes stale: a comment thread, the board and the inbox badge. Without it each of the three hand-rolls a loop. |
| Emoji picker and reaction control | `webbpulse-typescript` | Not a platform gap. The allow list of 24 is product content and stays in the product. |

# M2 API contract: issues

Fixed shape both halves build against, in the M1 style: routes under `/api`, list bodies are objects with one plural key, timestamps ISO 8601 UTC, ids ULIDs, platform error envelope, and a caller outside a workspace sees 404 never 403. Issues are workspace scoped so links and "my issues" can cross teams; `team_id` is a field, not a path segment. The `issues` domain serves every route here and consumes its own table stream for the rollup.

Route prefix for the gateway: `/api/workspaces/{workspace_id}/issues`.

## Routes (`issues` domain)

| Method and path | Body in | Body out | Who |
|---|---|---|---|
| `GET /workspaces/{workspace_id}/issues` | query `team_id?`, the repeatable filters below, `due_before?`, `due_after?`, `q?` (key or title prefix, case insensitive), `sort?` (`updated_desc` default, `created_desc`, `key_asc`, `priority_desc`, `due_asc`, `sla_asc` (soonest SLA breach first, issues without a running SLA last), `manual`), `cursor?`, `limit?` (1 to 100, default 50) | `{"issues": [Issue], "next_cursor": string or null}`; only issues in teams the caller can see; without `team_id` the read fans out across visible teams and merges by the sort key | team reader |
| `POST /workspaces/{workspace_id}/issues` | `{"team_id", "title", "body"?, "status_id"?, "priority"?, "assignee_id"?, "label_ids"?, "estimate"?, "start_date"?, "due_date"?, "parent_id"?}` | `Issue`, 201; key allocated from the team counter; status defaults to the lowest position `backlog` status | team member (workspace owner, admin or member, or a guest with a team membership) |
| `GET /workspaces/{workspace_id}/issues/{issue_id}` | none | `Issue` | team reader |

| `PATCH /workspaces/{workspace_id}/issues/{issue_id}` | any of `title`, `body`, `status_id`, `priority`, `assignee_id`, `label_ids`, `estimate`, `start_date`, `due_date`, `parent_id`, `sort_order`, `team_id` is never changeable | `Issue`; one `Activity` row per changed field, none for `sort_order` | team member |

| `POST /events` | stream records | consumer only; a gateway request 404s | none |

## List filters

Every filter below repeats (`status_id=a&status_id=b`), a single value still works, and values within one key are any of while different keys must all hold. Each has a `_not` form that excludes any issue matching one of its values.

| Key | Negation | Values |
|---|---|---|
| `status_id` | `status_id_not` | status ids |
| `status_category` | `status_category_not` | `backlog`, `unstarted`, `started`, `completed`, `cancelled` (`canceled` accepted); anything else is 422 |
| `assignee_id` | `assignee_id_not` | user ids, `me` for the caller, `none` for unassigned |
| `creator_id` | `creator_id_not` | user ids, `me` for the caller |
| `subscriber_id` | none | `me` or the caller's own id only; anyone else is 422, and a share link refuses it |
| `label_id` | `label_id_not` | label ids (any of), `none` for unlabelled; `label_id_not=none` keeps only labelled issues |
| `priority` | `priority_not` | the priority values, `none` being the literal priority |
| `project_id` | `project_id_not` | project ids, `none` for no project |
| `cycle_id` | `cycle_id_not` | cycle ids, `none` for no cycle |
| `parent_id` | none | an issue id, `none` for top level issues |
| `sla_status` | none | `none`, `on_track`, `at_risk`, `breached`; anything else is 422. Computed against the clock, so a delta sync (`updated_since`) does not notice an issue crossing into at risk or breached |

`due_before` and `due_after` are strict and exclude undated issues. Filtering runs in the handler over the per team index reads, so no index is added for it; a cursor carries a fingerprint of the filter and starts over when carried to a different one. The My issues filters are the exception: `subscriber_id=me`, a single `creator_id` and a single `assignee_id` read a keyed index instead of fanning out (`subscriptions` `user_id-workspace_id-index`, `issues` `created_by-workspace_id-index` and `ws_assignee-updated_at-index`, the first two `KEYS_ONLY` and resolved with a batch get), capped at 1000 rows, then narrowed to the caller's visible teams and the rest of the filter.

`sort=manual` orders by `sort_order` ascending, then id, with issues that were never placed after the rest. `sort_order` is a client chosen fractional index over `[0-9A-Za-z]`, 1 to 64 characters, which sorts the same bytewise everywhere; moving a row between two others is one patch with a key between theirs.

## SLA timers

`GET /workspaces/{workspace_id}/teams/{team_id}/sla-settings` (team reader) answers `SlaSettings`: `team_id`, `enabled` (default false), `urgent_hours` (default 24), `high_hours` (default 72), `medium_hours` and `low_hours` (default null), `updated_at`. `PATCH` (team admin) takes any of those fields; a null hours field removes that priority's rule, hours run 1 to 2160, and an absent field is left alone. The row is `team#<team_id>#sla` in `team_config` and goes with the team. Turning SLAs on or setting a rule's hours needs the Business plan (403 `PLAN_FEATURE_UNAVAILABLE`); turning them off or removing a rule never does, and a downgrade leaves saved rules and running timers alone.

Following Linear, an open issue of a priority with a rule gets a timer when it is created, leaves triage or reopens: `sla_started_at` is that moment and `sla_breaches_at` is it plus the priority's hours. Changing priority or team keeps the start and moves the deadline, or drops the timer when the new priority has no rule. Moving between open statuses keeps it. Completing, cancelling, archiving or sending the issue back to triage drops it. An issue is at risk once a quarter of its window is left, capped at 24 hours before the deadline, and breached from the deadline on.

The hourly due date sweep also writes `sla_at_risk` and `sla_breached` notifications to the assignee, once each per deadline; a breach older than 7 days sends nothing.

## Bulk update

`IssueBulkUpdate`: `issue_ids` (1 to 50, repeats collapsed) and `patch`, any of `status_id`, `assignee_id`, `priority`, `add_label_ids`, `remove_label_ids`, `project_id`, `cycle_id`, `estimate`. An explicit null clears; an absent field is left alone. A label may not be both added and removed.

Validation is all or nothing: every issue is read and authorized as a single patch would be, and every value checked against its issue's team, before any write. Any missing or invisible id is 404, a team the caller cannot write is 403, and a value one issue's team refuses (a status or label from another team, an assignee outside it) is 422, each with nothing written. Writes then run one issue at a time, each recording its own activity exactly as a single patch does. An issue deleted between the check and its write is returned in `skipped` rather than failing the rest, since the others are already written. Response `issues` keeps request order.

## Shapes

`Issue`: `id`, `workspace_id`, `team_id`, `key` (`<KEY_PREFIX>-<number>`, denormalised, indexed by `ws_team-key_number-index`), `number`, `title` (1 to 200 chars), `body` (markdown, nullable, at most 65536 bytes), `status_id`, `priority` (`"none" | "urgent" | "high" | "medium" | "low"`, default `"none"`), `assignee_id` (nullable, must be a team reader), `label_ids` (list, each must exist on the team), `estimate` (nullable string validated against the team's `estimate_scale`: `off` accepts only null, `exponential` one of `1 2 4 8 16`, `fibonacci` one of `1 2 3 5 8`, `linear` `1` to `5`, `tshirt` one of `XS S M L XL`, plus the extended values and `0` when the team's toggles add them; a value an issue already holds is kept on a write that echoes it, so a scale switch never refuses or rewrites it; T-shirt sizes weigh XS=1 S=2 M=3 L=5 XL=8 XXL=13 XXXL=21 points), `start_date` and `due_date` (nullable `YYYY-MM-DD`, `due_date` never before `start_date`), `parent_id` (nullable, same team, no cycles, at most one level deep in the MVP: a child cannot itself have children), `sort_order` (nullable, see List filters), `progress` (`{"total", "completed"}` counting direct children, `completed` being children whose status category is `completed` or `cancelled`, maintained by the rollup consumer), `blocked_by_open_count` (how many `blocked_by` links point at an issue whose status category is neither `completed` nor `cancelled`, recounted on every link write and by the rollup consumer when a blocker's status moves, and counting blockers in teams the caller cannot see, so it discloses only that one exists), `sla_started_at` and `sla_breaches_at` (nullable timestamps, see SLA timers), `sla_status` (`"none" | "on_track" | "at_risk" | "breached"`, computed on read; `none` for an archived issue), `created_by`, `created_at`, `updated_at`.

`Link`: `link_id`, `issue_id`, `type` (`"blocks" | "blocked_by" | "relates_to" | "duplicate_of"`), `target_issue_id`, `target_key`, `target_title`, `target_status` (`{"id", "name", "category"}` of the far side's status, from its own team, nullable), `created_by`, `created_at`. Writing `duplicate_of` moves the source to its team's first `cancelled` status unless it is already `completed` or `cancelled`, recorded as the caller's own `status_id` change; removing the link leaves the status alone. Storage keeps one row per direction on `relations` so both issues list the pair; `blocks` on A is `blocked_by` on B, `relates_to` is symmetric, `duplicate_of` on A is `duplicated_by` on B and only the canonical direction is accepted on write. `link_id` is stable across both rows.

`Activity`: `activity_id`, `issue_id`, `actor_id`, `actor_kind` (`"user" | "system" | "github"`), `kind` (`"created" | "field_changed" | "link_added" | "link_removed" | "child_added" | "child_removed"`), `field` (nullable, the changed field name), `from` and `to` (nullable JSON values, label and status changes carry ids; `link_added.to`, `link_removed.from`, `child_added.to` and `child_removed.from` carry `{"id", "key", "title"}` of the other issue, with `field` holding the link type as seen from this issue, while rows written before that carry the bare id), `source` (nullable, `"web" | "mcp" | "cli" | "api" | "github" | "system"`, the client the change came through, derived from the credential; null on rows written before it was recorded), `created_at`. A parent change writes `child_removed` on the old parent and `child_added` on the new one beside the child's own `parent_id` change, including on create and on delete. Activity is written by the request handler in the same call, never by the consumer, so a failed write never leaves history behind.

## Keys, counters and the rollup

Key allocation is one `update` on `counters` with `ADD next_number :one` and `return_values="UPDATED_NEW"`, no transaction; a crash between allocation and the issue put leaves a gap and nothing renumbers. The `issues` table streams `NEW_AND_OLD_IMAGES`; the issues function consumes its own stream on `/events` (the `dynamodb_stream_event_sources` wiring in the lambda-function module, being added upstream; until it lands the consumer is reachable in tests and Root A only). The consumer recomputes `progress` on the old and new parent when `parent_id` or the status category changes, with `ReportBatchItemFailures`, and is idempotent because it recounts from `ws_parent-created_at-index` rather than incrementing.

## Auto-close

`GET` and `PATCH /workspaces/{workspace_id}/teams/{team_id}/auto-close-settings` (`teams` domain; read for team readers, write for team admins) hold `period_months` (`1 | 3 | 6 | 9 | 12`, null for off, the default) and `status_id` (a visible `cancelled` status of the team, null for the first one; any other status is a 422). The answer adds `team_id`, `enabled` and `updated_at`. On the hour, after the cycle close sweep and before auto-archive, the issues function closes every opted-in team's backlog and triage issues whose `updated_at` is older than the period: the issue moves to the chosen cancelled status, or the first visible one, leaves triage, and gets a `field_changed` `status_id` activity row with `actor_kind` and `source` `system`. Unstarted, started, archived and snoozed triage issues are left alone, a team with no cancelled status is skipped, an issue edited after the sweep read it is skipped, and one run closes at most 200 issues per column. The MCP tool is `update_team_auto_close_settings`, and `get_team` answers `auto_close_settings`.

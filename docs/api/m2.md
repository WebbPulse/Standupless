# M2 API contract: issues

Fixed shape both halves build against, in the M1 style: routes under `/api`, list bodies are objects with one plural key, timestamps ISO 8601 UTC, ids ULIDs, platform error envelope, and a caller outside a workspace sees 404 never 403. Issues are workspace scoped so links and "my issues" can cross projects; `project_id` is a field, not a path segment. The `issues` domain serves every route here and consumes its own table stream for the rollup.

Route prefix for the gateway: `/api/workspaces/{workspace_id}/issues`.

## Routes (`issues` domain)

| Method and path | Body in | Body out | Who |
|---|---|---|---|
| `GET /workspaces/{workspace_id}/issues` | query `project_id?`, `status_id?`, `assignee_id?` (`me` allowed), `label_id?`, `parent_id?`, `priority?`, `q?` (key or title prefix, case insensitive), `sort?` (`updated_desc` default, `created_desc`, `key_asc`, `priority_desc`, `due_asc`), `cursor?`, `limit?` (1 to 100, default 50) | `{"issues": [Issue], "next_cursor": string or null}`; only issues in projects the caller can see; without `project_id` the read fans out across visible projects and merges by the sort key | project reader |
| `POST /workspaces/{workspace_id}/issues` | `{"project_id", "title", "body"?, "status_id"?, "priority"?, "assignee_id"?, "label_ids"?, "estimate"?, "start_date"?, "due_date"?, "parent_id"?}` | `Issue`, 201; key allocated from the project counter; status defaults to the lowest position `backlog` status | project member (workspace owner, admin or member, or a guest with a project membership) |
| `GET /workspaces/{workspace_id}/issues/{issue_id}` | none | `Issue` | project reader |
| `GET /workspaces/{workspace_id}/issues/by-key/{key}` | none | `Issue`; key is `ABC-123`, case insensitive | project reader |
| `PATCH /workspaces/{workspace_id}/issues/{issue_id}` | any of `title`, `body`, `status_id`, `priority`, `assignee_id`, `label_ids`, `estimate`, `start_date`, `due_date`, `parent_id`, `project_id` is never changeable | `Issue`; one `Activity` row per changed field | project member |
| `DELETE /workspaces/{workspace_id}/issues/{issue_id}` | none | 204; children are reparented to null, links and activity for it are removed | project admin, or the creator while it has no children |
| `GET /workspaces/{workspace_id}/issues/{issue_id}/children` | query `cursor?`, `limit?` | `{"issues": [Issue], "next_cursor"}` ordered by `created_at` | project reader |
| `GET /workspaces/{workspace_id}/issues/{issue_id}/links` | none | `{"links": [Link]}` both directions, the inverse read from `ws_target-relation_type-index` | project reader |
| `POST /workspaces/{workspace_id}/issues/{issue_id}/links` | `{"type", "target_issue_id"}` | `Link`, 201; idempotent on the same pair and type; 404 when the target is not visible to the caller; 422 on self link | project member on the source; target needs reader |
| `DELETE /workspaces/{workspace_id}/issues/{issue_id}/links/{link_id}` | none | 204 | project member on the source |
| `GET /workspaces/{workspace_id}/issues/{issue_id}/activity` | query `cursor?`, `limit?` (default 50) | `{"activity": [Activity], "next_cursor"}` newest first | project reader |
| `POST /events` | stream records | consumer only; a gateway request 404s | none |

## Shapes

`Issue`: `id`, `workspace_id`, `project_id`, `key` (`<KEY_PREFIX>-<number>`, denormalised, indexed by `ws_project-key_number-index`), `number`, `title` (1 to 200 chars), `body` (markdown, nullable, at most 65536 bytes), `status_id`, `priority` (`"none" | "urgent" | "high" | "medium" | "low"`, default `"none"`), `assignee_id` (nullable, must be a project reader), `label_ids` (list, each must exist on the project), `estimate` (nullable string validated against the project's `estimate_scale`: `off` accepts only null, `fibonacci` one of `1 2 3 5 8 13 21`, `linear` `1` to `10`, `tshirt` one of `XS S M L XL`), `start_date` and `due_date` (nullable `YYYY-MM-DD`, `due_date` never before `start_date`), `parent_id` (nullable, same project, no cycles, at most one level deep in the MVP: a child cannot itself have children), `progress` (`{"total", "completed"}` counting direct children, `completed` being children whose status category is `completed` or `cancelled`, maintained by the rollup consumer), `created_by`, `created_at`, `updated_at`.

`Link`: `link_id`, `issue_id`, `type` (`"blocks" | "blocked_by" | "relates_to" | "duplicate_of"`), `target_issue_id`, `target_key`, `target_title`, `created_by`, `created_at`. Storage keeps one row per direction on `relations` so both issues list the pair; `blocks` on A is `blocked_by` on B, `relates_to` is symmetric, `duplicate_of` on A is `duplicated_by` on B and only the canonical direction is accepted on write. `link_id` is stable across both rows.

`Activity`: `activity_id`, `issue_id`, `actor_id`, `actor_kind` (`"user" | "system" | "github"`), `kind` (`"created" | "field_changed" | "link_added" | "link_removed" | "child_added" | "child_removed"`), `field` (nullable, the changed field name), `from` and `to` (nullable JSON values, label and status changes carry ids), `created_at`. Activity is written by the request handler in the same call, never by the consumer, so a failed write never leaves history behind.

## Keys, counters and the rollup

Key allocation is one `update` on `counters` with `ADD next_number :one` and `return_values="UPDATED_NEW"`, no transaction; a crash between allocation and the issue put leaves a gap and nothing renumbers. The `issues` table streams `NEW_AND_OLD_IMAGES`; the issues function consumes its own stream on `/events` (the `dynamodb_stream_event_sources` wiring in the lambda-function module, being added upstream; until it lands the consumer is reachable in tests and Root A only). The consumer recomputes `progress` on the old and new parent when `parent_id` or the status category changes, with `ReportBatchItemFailures`, and is idempotent because it recounts from `ws_parent-created_at-index` rather than incrementing.

## Tables this milestone adds

`issues`, `relations`, `activity`, `counters` (already declared in M1, `project#<pid>#issue` counter key) per `docs/design.md` section 3. Status validation reads `project_config`, membership reads `memberships`, project reads `projects`, all read only.

# M6 API contract: programmatic access

Fixed shape both halves build against, in the M1 to M5 style: routes under `/api`, list bodies are objects with one plural key, timestamps ISO 8601 UTC, ids ULIDs, platform error envelope, and a caller outside a workspace sees 404 never 403.

M6 adds no domain. Design section 1 already assigns every surface here to a domain that exists: API keys to `workspaces` under `/api/api-keys`, share links and the public read to `views` under `/api/share-links` and `/api/shared`, the OAuth authorization server to `identity`, and the MCP transport to `integrations` at `/api/mcp`. A new `access` domain would have split the API key routes from the membership rows they intersect against and the share links from the saved views they resolve, so both would have needed a read grant on another domain's table for no gain. The one thing M6 does add is a table each for keys and share links, and the three credential paths into the one `AuthzContext`.

The project's claim is that three credential kinds resolve to one authorization context. That is not three code paths that agree; it is one path. A user's JWT, an API key and an MCP access token all land on `require(...)` in `app/common/api/dependencies/authz.py`, which reads claims through `webbpulse.identity.claims`, reads the live membership row, and answers an `AuthzContext`. What differs between them is only what narrows afterwards: a JWT narrows to nothing, a key and a token narrow to their scopes, intersected against live membership on every request.

Route prefixes for the gateway, matching `lambda_domain_path_prefixes` in `terraform/apigateway.tf`:

| Domain | Prefix | Authorizer |
|---|---|---|
| `workspaces` | `/api/workspaces/{workspace_id}/api-keys` | JWT |
| `views` | `/api/workspaces/{workspace_id}/share-links` | JWT |
| `views` | `/api/shared` | NONE |
| `identity` | `/api/auth/.well-known/oauth-authorization-server` | NONE, under the `/api/auth` prefix |
| `identity` | `/api/auth/.well-known/oauth-protected-resource` | NONE, under the `/api/auth` prefix |
| `identity` | `/api/auth/authorize`, `/api/auth/token`, `/api/auth/register-client` | NONE |
| `integrations` | `/api/mcp` | NONE at the gateway, OAuth bearer in process |

`/api/shared` sits outside the workspace prefix because an anonymous reader has no workspace to put in a path and no membership that would let them name one: the token is what resolves the workspace, after it has already resolved the single row it grants.

`/api/mcp` carries `authorization_type = "NONE"` at the gateway for one reason: an MCP client must be able to reach the endpoint unauthenticated to receive the `WWW-Authenticate` challenge naming the authorization server, which is how the discovery handshake starts. The route is not public. Every request that carries a body is refused without a verified bearer, in process, before anything reads a table.

The `identity` domain's `/api/api-keys` routes are under the workspace prefix rather than beside `/api/auth` because a key is minted inside one workspace and its scopes intersect one membership row. There is no account-wide key.

## The three credential kinds

| Kind | Presented as | Verified by | Scopes | Actor |
|---|---|---|---|---|
| User session | `Authorization: Bearer <RS256 access token>` | The gateway's JWT authorizer, or the staging gate | none, so nothing narrows | `user` |
| API key | `Authorization: Bearer wpk_<random>` | `webbpulse.identity.api_keys.verify` in process | the key's stored set, intersected live | `api_key` |
| MCP token | `Authorization: Bearer <RS256 access token with `scope`>` | `webbpulse.identity.JwksVerifier` in process, on the `integrations` function | the token's granted `scope`, intersected live | `api_key` |

An MCP token is an ordinary product access token, and what makes it narrower is the `scope` claim the authorization server put on it. It does not verify at the gateway, though: `ANY /api/mcp` carries `authorization_type = "NONE"` so the endpoint can answer the discovery challenge itself, so no authorizer runs on that route and the `integrations` function verifies the bearer in process. Verification is the identity package's `JwksVerifier` against the issuer's published key set, checking RS256, `iss`, `exp`, `nbf` and `aud`. The audience is the RFC 8707 resource the token is bound to, `IDENTITY_MCP_RESOURCE_URL`, which is the MCP endpoint's own URL rather than `IDENTITY_AUDIENCE`, so the `integrations` function carries that variable alongside the issuer every domain already holds. Nothing after verification differs from an API key: the same claims shape, the same `resolve_context`, the same live intersection.

There are no root level `/.well-known` route keys. Both discovery documents are served under the issuer at `/api/auth/.well-known/...`, which is where the package mounts them and what the MCP endpoint's `WWW-Authenticate` header names as `resource_metadata`, so the root level keys that had been declared answered only 404 and were removed.

An API key cannot verify at the gateway, because a gateway JWT authorizer cannot verify something that is not a JWT. In staging the gate passes it through unverified on the strength of its prefix, per `identity_jwt.api_key_prefixes` in `terraform/staging_access_gate.tf`, and the function verifies it. In production the native JWT authorizer would reject it outright, so every API key route carries `authorization_type = "NONE"` on its own route key and verifies in process. That is the same shape M5's webhook route uses and for the same reason: the credential is not the one the gateway knows how to check.

**Scopes narrow, never widen.** `effective_scopes(key.scopes, live_scopes(membership))` is computed per request against the membership row read in that request. A key minted by an admin who has since become a member carries an admin's stored scope set and spends a member's. A key whose minter has been removed from the workspace intersects against the empty set and can spend nothing, which is the same 404 a non-member gets, because the membership read fails before the intersection is reached.

Scopes, `API_KEY_SCOPES` in `app/common/db/dynamo/api_keys.py`:

| Scope | Grants |
|---|---|
| `issues:read` | Read issues, their comments, relations, subscribers and activity, and search |
| `issues:write` | Create, update, assign, archive, relate and bulk edit issues; subscribe and unsubscribe; delete a relation |
| `comments:write` | Add a comment to an issue the caller can read |
| `teams:read` / `teams:write` | Read teams; create and update them, including cycle and archive settings |
| `members:read` / `members:write` | Read workspace and team members and invites; add, remove, join, leave, invite and change roles |
| `statuses:read` / `statuses:write` | Read a team's workflow; create, update, reorder and delete statuses |
| `labels:read` / `labels:write` | Read labels; create, update and delete them |
| `projects:read` / `projects:write` | Read projects, project updates and the roadmap; create, update and delete them |
| `milestones:read` / `milestones:write` | Read project milestones; create, update and delete them |
| `cycles:read` / `cycles:write` | Read cycles, velocity and history; create, update and delete cycles and move issues in and out |
| `releases:read` / `releases:write` | Read releases, release pipelines and the releases an issue shipped in; record, advance, edit and delete releases, set a team's pipeline and backfill releases from past deployments |
| `views:read` / `views:write` | Read saved views and the board; create, update and delete views |
| `notifications:read` / `notifications:write` | Read the caller's inbox; mark, snooze and clear it |
| `settings:read` / `settings:write` | Read workspace settings; change them |
| `admin` | Act with the workspace-admin role, alongside the resource scope. Live only for an owner or admin |

A scope is a ceiling on a role, never a substitute for it. `issues:write` on a key minted by a guest still reaches only that guest's teams, because the capability check runs first and the scope check second. A route or tool that needs the workspace-admin role (settings changes, workspace membership and invites) needs `admin` plus its resource scope, and `admin` is live only while the credential's user is an owner or admin, so a member's key carrying `admin` is still a 403. Team-admin actions such as editing labels or statuses do not need `admin`. Deleting a team is workspace-admin work, so the `delete_team` tool needs `teams:write` plus `admin`. No API key reaches deleting a workspace or a team over REST, billing, API keys, OAuth clients, the GitHub App, webhooks or share links: those routes refuse every key.

**Legacy aliases.** Keys and tokens minted when there were five scopes keep working. `teams:read` satisfies `members:read`, `statuses:read`, `labels:read`, `projects:read`, `milestones:read`, `cycles:read` and `settings:read`; `views:read` satisfies `notifications:read`; `issues:write` satisfies `labels:write` and `projects:write`. `LEGACY_SCOPE_ALIASES` holds the map and `satisfies` applies it, for REST and MCP alike. An old credential is read as holding the whole finer scope, including verbs added since, such as deleting a label.

REST enforces this inside `require(...)` rather than at each route. The scope a route needs is recorded once per method and path in `ROUTE_SCOPES` in `app/common/api/dependencies/scopes.py`, because the capability a route declares does not determine it: `GET /issues` and `POST /issues` both declare `workspace:read`. A route the table does not name, and one it maps to no scope, refuse every key with a 403 `INSUFFICIENT_SCOPE`, the same code the MCP path reports through `-32003`. A session carries no scopes and skips the check entirely.

## API keys (`workspaces` domain)

| Method and path | Body in | Body out | Who |
|---|---|---|---|
| `GET /workspaces/{workspace_id}/api-keys` | query `scope?` (`mine` default, `workspace` for every key in the workspace) | `{"api_keys": [ApiKey]}` newest first | `mine`: any member. `workspace`: workspace admin |
| `POST /workspaces/{workspace_id}/api-keys` | `{"name", "scopes", "kind"?, "expires_in_days"?}` | `ApiKeyCreated`, 201 | member for `kind` `user`, workspace admin for `kind` `workspace` |
| `DELETE /workspaces/{workspace_id}/api-keys/{key_id}` | none | 204 | the key's owner, or a workspace admin |

`POST` is the only response that ever carries `secret`. The stored row holds a SHA-256 of it and nothing else, so there is no route that shows it again and no support path that can recover it. A lost key is revoked and reminted.

`kind` is `user` or `workspace`, default `user`.

- A **per-user key** acts as its minter. Its `sub` is that user, its scopes intersect that user's live membership, and it dies with their membership. It is the key a software engineer puts in their own shell.
- A **per-workspace key** acts as the workspace rather than as a person, for a service that must outlive whoever set it up. Its `sub` is the synthetic principal `svc#<workspace_id>`, and it intersects against a fixed service scope set rather than a membership row: the workspace's own existence is what keeps it alive, and deleting the workspace kills it. Only a workspace admin may mint one, and it may never carry `admin`, so a service key is still narrower than an admin.

A per-workspace key's `AuthzContext` carries `role` `member` and `actor` `api_key`. It is deliberately not an admin: a credential nobody's departure revokes must not be able to change who is in the workspace.

`scopes` must be a non-empty subset of `API_KEY_SCOPES`. An empty list is a 422 rather than a key that can do nothing, because a key that authenticates and then refuses everything is harder to diagnose than one that was never minted.

`expires_in_days` is 1 to 365, or absent for a key that does not expire. An expired key stays in the list and stays visible, which is the platform's own `ApiKeyStore` decision: a key that vanished would be indistinguishable from one that never existed.

Live keys per workspace are capped by the plan limits (see `m1.md`), counting both kinds and not counting revoked ones.

## Share links (`views` domain)

| Method and path | Body in | Body out | Who |
|---|---|---|---|
| `GET /workspaces/{workspace_id}/share-links` | query `target_type?` (`issue`, `view`), `target_id?` | `{"share_links": [ShareLink]}` newest first | any member; a guest sees only links onto teams they can read |
| `POST /workspaces/{workspace_id}/share-links` | `{"target_type", "target_id", "expires_in_days"?}` | `ShareLinkCreated`, 201 | a member, admin or owner who can read the target and write in its team; a guest gets 403 |
| `DELETE /workspaces/{workspace_id}/share-links/{token_hash}` | none | 204 | the link's creator, or a team admin on the target's team |

| Method and path | Body in | Body out | Who |
|---|---|---|---|
| `GET /shared/{token}` | none | `SharedTarget` | nobody; the token is the credential |
| `GET /shared/{token}/issue` | none | `SharedIssue` | nobody |
| `GET /shared/{token}/view` | query `cursor?`, `limit?` (1 to 100, default 50) | `{"issues": [SharedIssueSummary], "next_cursor"}` | nobody |

`GET /shared/{token}` is the one an anonymous page loads first. It answers what kind of target the token resolves to and the minimum needed to render a heading, so the reader's client knows which of the two reads to make next. A token that does not resolve, has expired, or has been revoked is a 404 with no detail, identical in all three cases.

**A share link widens nothing.** The token resolves to exactly one row: one `issue_id`, or one `view_id`. The read then runs under a service context carrying no user, and every field it can reach is bounded by that one row:

- An issue share exposes that issue's title, body, status, priority, labels, estimate, dates, assignee display name, and its comments. It does not expose sub-issues, linked issues, activity, attachments' presigned URLs, or the identity of anyone who is not on the issue.
- A view share exposes the issues that the saved view's filter selects **inside the one team the view is scoped to**, with the summary fields of `SharedIssueSummary` and nothing else. A personal view whose filter spans every visible team cannot be shared: `POST` refuses it with 422, because "every team the creator can see" is not a bound that survives the creator's membership changing.
- Neither read follows a link out of its target. There is no route under `/shared` that takes an issue id, so a reader holding a token for issue A cannot ask for issue B.

Optional auth, per design section 2: these three routes carry `authorization_type = "NONE"`, so no claims arrive from the gateway. A signed-in reader who follows a share link is still anonymous to these routes, which is deliberate: the answer must not depend on who is asking, or the same link would render two different pages and a share would become a way to probe membership. The frontend's share page therefore renders the same for everyone and links to the authenticated issue page when the reader turns out to have a session.

`expires_in_days` is 1 to 365, or absent for a link that does not expire, and is carried as the table's TTL. At most 200 live links per workspace.

Revocation is by `token_hash` rather than by token, because the list is what a settings page has and the token is what it deliberately does not: the plaintext token is shown once on create and stored only as its SHA-256, exactly as an API key is.

## The OAuth authorization server (`identity` domain)

Mounted by `webbpulse.identity.build_identity_router` behind `mcp_oauth_enabled`, at the issuer's own prefix. No product code implements any of it; the product supplies the three stores and the tenant resolver.

| Path | What |
|---|---|
| `GET /api/auth/.well-known/oauth-authorization-server` | Authorization server metadata: the endpoints, `code_challenge_methods_supported` `["S256"]`, `grant_types_supported` `["authorization_code", "refresh_token"]`, `response_types_supported` `["code"]`, `token_endpoint_auth_methods_supported` `["none"]`, and every scope in `API_KEY_SCOPES` |
| `GET /api/auth/.well-known/oauth-protected-resource` | Protected resource metadata naming `/api/mcp` as the resource and this server as its authorization server |
| `GET /api/auth/authorize` | The authorization endpoint. PKCE S256 required; a request with no `code_challenge`, or one naming `plain`, is refused |
| `POST /api/auth/authorize/consent` | Consent, which names the workspace the token will be bound to |
| `POST /api/auth/token` | The token endpoint. `authorization_code` and `refresh_token` only |
| `POST /api/auth/register-client` | Dynamic client registration for public PKCE clients |
| `POST /api/auth/revoke` | Token revocation |

The registration path is `/register-client`, not `/register` as design section 5 writes it. The package named it that way and the package publishes its own metadata document, so the document and the route agree; the design doc's spelling is the one that is wrong.

**Consent names one workspace, and the token is bound to it.** A user who belongs to three workspaces picks one, and the issued token carries that workspace as its tenant claim. There is no token that spans workspaces, and no way to exchange a token for one in another workspace: the client authorizes again. That is what makes an MCP token's blast radius the same as an API key's.

Granted scopes are the intersection of what the client asked for, the scopes this product supports, and what the consenting user's membership in the chosen workspace actually allows. A guest consenting to `issues:write` gets `issues:write`, which still reaches only their teams.

**Defaults include `admin`.** A client that names no scope is granted all of `API_KEY_SCOPES` (`MCP_SCOPES` in `app/domains/identity/oauth_server_glue.py`). The Claude connectors do not let a person pick scopes, so leaving `admin` out would make workspace administration unreachable by MCP for every owner. It is safe because every call intersects with the live role: `admin` does nothing for a member or guest, and nothing it unlocks is irreversible at workspace level; the one irreversible tool it reaches, `delete_team`, removes a single team and is marked destructive so the client asks first.

**A refresh never widens a grant.** A refreshed token carries the scopes the user consented to, or a requested subset of them. A connection authorized before the scope set grew keeps its old scopes, read through the legacy aliases, and must authorize again to gain the new write, settings and admin tools.

No client secret, for any client. `token_endpoint_auth_methods_supported` is `["none"]` because every MCP client is a public client: a desktop editor cannot hold a secret. PKCE is what stands in for one, and S256 is the only method accepted.

Dynamic registration is open, which is the judgement call design section 5 records and this contract takes: a Claude or editor client connects without the workspace owner registering it first. It is rate limited per IP by the package at 10 registrations an hour, a registration expires under `mcp_client_ttl` if no token is ever issued to it, and a registered client can do nothing at all until a human completes the consent screen. The exposure is a registration row, not access.

## MCP (`integrations` domain)

| Method and path | Body in | Body out | Who |
|---|---|---|---|
| `POST /mcp` | A JSON-RPC 2.0 request or notification | A JSON-RPC 2.0 response, or 202 for a notification | a bearer carrying the scopes the called tool needs |
| `GET /mcp` | none | 405 with `WWW-Authenticate` naming the authorization server | nobody |
| `DELETE /mcp` | none | 204 | a bearer; ends the session |

Streamable HTTP transport. One endpoint, `POST` carrying the request and the response coming back in the body. No SSE stream in the MVP: nothing this server does is long-running enough to need one, and a server-sent event stream through an HTTP API and a Lambda is a 29 second timeout wearing a streaming interface.

A request with no bearer, or one whose bearer does not verify, is 401 carrying `WWW-Authenticate: Bearer resource_metadata="<issuer>/.well-known/oauth-protected-resource"`, which is the discovery handshake: an MCP client reads that header, fetches the metadata, finds the authorization server and starts the PKCE flow. That header is the only thing an unauthenticated caller ever gets from this endpoint.

Methods: `initialize`, `tools/list`, `tools/call`, `ping`. No `resources/*`, no `prompts/*`, no `sampling/*`.

Every tool's full description and input schema are what `tools/list` answers; the table is the one-line summary. Teams are accepted as an id, a key such as `ENG` or a name; issues as an id or a key such as `ENG-12`; people as `me`, an email or an id; statuses, labels, cycles, projects, initiatives, milestones and views by id or unambiguous name. A name matching more than one row is refused with a request for the id.

Each tool calls the same `app.common` read or write path its route does (`issue_writes`, `issue_links`, `issue_subscribers`, `comment_writes`, `labels`, `team_writes`, `team_members`, `team_workflow`, `cycle_writes`, `milestone_writes`, `project_writes`, `project_updates`, `initiative_writes`, `saved_views`, `inbox`, `workspace_members`) and runs the route's `Capability` check, so role checks, validation and the activity row are one implementation and a tool never does more than the signed-in person could. A route error comes back as a tool result with `isError`: a 404 as the same not-found an invisible row gets, a 403 as a refusal to write there. The cycle issue tools go through the bulk issue patch, so they need `issues:write` like `PATCH /issues`.

Destructive tools carry `destructiveHint: true` and say in their description what is lost. `delete_team` also carries `idempotentHint: true`: it runs the delete route's own path, tombstoning the team and starting the team purge chain, and a repeat call changes nothing further. Read tools carry `readOnlyHint: true`. `update_member_role` and `invite_member` refuse the `owner` role, so ownership never moves through MCP.

Deliberately absent: deleting a workspace, deleting an issue or a comment, billing and Stripe, minting API keys or OAuth clients, GitHub App installation, and ownership transfer. Each is irreversible at workspace level or mints a credential, and stays a signed-in UI action.

A tool call whose scopes the bearer does not carry is a JSON-RPC error with code `-32003` and an `INSUFFICIENT_SCOPE` payload, rather than a transport-level 403, because the transport request itself was authorized and it is the tool that was not. A call naming an unknown tool is `-32601`.

Every tool writes through the same repositories the HTTP routes use, so an issue created by an agent carries the same activity row, the same key allocation and the same stream record as one created in the UI. There is no MCP-shaped write path.

## Published OpenAPI

The merged Root A document, `app/common/composition/app.py`, is emitted to a file by `backend/scripts/export_openapi.py` and written to `backend/openapi.json`. That is the whole of what M6 builds: one script, run in CI on every backend change, so the committed document cannot drift from the served one.

The document is the merged one rather than a per-domain one, because a caller reaching `api.standupless.dev` sees one API and does not know or care which function serves a path. The `/api/auth` routes the identity package contributes are in it too, for the same reason.

Publishing it to a URL is not in M6. The org workflow `openapi-publish.yml` that design section 6 names does not exist, and building it is an org-level change rather than a product one.

## Shapes

`ApiKey`: `key_id` (ULID), `name`, `kind` (`"user" | "workspace"`), `prefix` (the clear-text fragment a person recognises a key by, `wpk_` plus the first eight characters), `scopes`, `created_by`, `created_at`, `expires_at` (nullable), `last_used_at` (nullable), `revoked_at` (nullable).

`ApiKeyCreated`: every field of `ApiKey`, plus `secret`, the plaintext, present on this one response and nowhere else.

`ShareLink`: `token_hash` (the id a list renders and a revoke names), `target_type` (`"issue" | "view"`), `target_id`, `team_id`, `title` (the target's own title, denormalised so a settings list needs no second read), `created_by`, `created_at`, `expires_at` (nullable), `url` (the absolute frontend URL, so the settings page does not compose it).

`ShareLinkCreated`: every field of `ShareLink`, plus `token`, the plaintext, present on this one response and nowhere else. `url` on this response carries the token; on every other response it carries the path with no token, because a list that carried live tokens would make the list itself a credential.

`SharedTarget`: `target_type`, `title`, `workspace_name`, `team_name`, `shared_at`. No ids that are useful anywhere else, and no creator identity.

`SharedIssue`: `issue_key`, `title`, `body`, `status` (`{"name", "category", "color"}`), `priority`, `labels` (`[{"name", "color"}]`), `estimate`, `start_date`, `due_date`, `assignee_name` (nullable display name, never a user id or an email), `created_at`, `updated_at`, `comments` (`[SharedComment]`).

`SharedComment`: `author_name`, `body`, `created_at`. No ids, no reactions, no edit history.

`SharedIssueSummary`: `issue_key`, `title`, `status`, `priority`, `assignee_name`, `updated_at`.

`ApiKeyScope`: the `API_KEY_SCOPES` strings, exported so the frontend renders checkboxes from the same list the backend validates against.

## Tables this project adds

Same notation as the earlier projects, per `docs/design.md` section 3.

| Table | PK | SK | GSIs | TTL / stream |
|---|---|---|---|---|
| `api_keys` | `workspace_id` | `key_id` | `key_hash-index` (hash `key_hash`) | TTL `expires_at` |
| `share_links` | `token_hash` | none | `ws_target-index` (hash `ws_target`, range `created_at`) | TTL `expires_at` |

`api_keys` differs from the platform's own `api-keys` spec, which partitions by `key_hash` with a `user_id-created_at-index`. This product's key is workspace scoped, and "every key in this workspace" is the query a settings page makes, which under the platform's spec would be a scan. Verification reads `key_hash-index` instead, which is one index query rather than one point read, and that is the cost the workspace listing buys. The product supplies its own `ApiKeyStore` over this table, so the platform's `verify`, `mint`, `revoke` and `effective_scopes` are still what run.

`share_links` partitions by `token_hash` exactly as design section 3 says, which is uniform by construction and makes the anonymous read a point lookup with no index behind it. `ws_target` is `<workspace_id>#<target_type>#<target_id>`, which is what makes "every link onto this issue" and "revoke everything pointing at this view" one query each.

The OAuth authorization server's three tables come from `webbpulse.identity.oauth_server_storage` and are not declared here. The platform identity module ships them from 2.27.0: `terraform/identity.tf` sets `oauth_server_enabled = true` and `oauth_server_mcp_resource_url`, which creates `oauth-clients`, `authorization-codes` and `oauth-consents`, extends the identity role's table grant to them, and puts `IDENTITY_MCP_OAUTH_ENABLED=true` and `IDENTITY_MCP_RESOURCE_URL` on the identity function through `module.identity.identity_environment`.

Repository bundles:

- `workspaces` adds `api_keys` for write. Its read set is unchanged.
- `views` adds `share_links` for write, and `activity` and `attachments` for read, which the shared issue read needs. It already reads `issues`, `comments`, `teams` and `team_config`.
- `integrations` adds `issues`, `relations`, `comments`, `counters`, `planning` and `subscriptions` for write, and `views` for read, because every MCP write tool goes through the same repository the owning domain's routes do. That is the second place in the product where a domain writes another's table, after M5's transition writes, and it is the same deliberate trade: the alternative is the MCP server calling its own HTTP API with a credential it would have to hold.

## Authorization rules

- Every `/api-keys` route declares a capability. The `mine` list and `POST` with `kind` `user` declare `Capability.WORKSPACE_READ`, then decide ownership in the handler. The `workspace` list and `POST` with `kind` `workspace` declare `Capability.WORKSPACE_ADMIN`. `DELETE` declares `WORKSPACE_READ` and refuses a key the caller neither owns nor administers, with a 404 rather than a 403, so a member cannot enumerate other people's key ids.
- **An API key can never mint or revoke an API key.** Every route under `/api-keys` refuses a context whose actor is not `user`, through `webbpulse.identity.scopes.is_api_key_actor`. A key that could mint its successor would make revocation meaningless.
- Every `/share-links` write route declares `Capability.WORKSPACE_READ` and then decides against the target's own team with `require_team_member`, which is the same shape M3's comment writes use. Creating a link onto something you can only read is not allowed: a share is a publication, and publishing is a write.
- The three `/shared` routes carry no dependency at all. They join `PUBLIC_ROUTES` in `tests/common/test_route_contract.py` beside M5's two GitHub entry points, so the fixture diff still surfaces a sixth.
- `/api/mcp` carries no route dependency either, and is the fourth allowlisted public route. The bearer check runs inside the handler because an unauthenticated request must receive the challenge header rather than the gateway's bare 401, and a dependency that raised before the handler could not set it.
- The OAuth server's routes are the package's own and carry the package's own guards. `/authorize` requires a signed-in user and redirects to the login page when there is none; `/token` and `/register-client` authenticate by PKCE and by rate limit respectively.

## The public route set

Seven route keys carry `authorization_type = "NONE"` after M6, up from two. Named individually in `terraform/apigateway.tf` rather than swept into a prefix:

| Route key | Credential |
|---|---|
| `POST /api/github/webhooks` | GitHub's HMAC over the raw body (M5) |
| `GET /api/github/callback` | The signed `state` this product minted (M5) |
| `ANY /api/shared/{proxy+}` | The share token in the path |
| `ANY /api/mcp` | An OAuth bearer, verified in process |
| `GET /.well-known/oauth-authorization-server` | none; public metadata |
| `GET /.well-known/oauth-protected-resource` | none; public metadata |
| `ANY /api/auth/{proxy+}` | already unauthenticated (M0), and the authorization server's endpoints land inside it |

The API key routes are not in this table. They sit behind the JWT authorizer like every other workspace route, because minting a key is a thing a signed-in person does. What is new is that the **routes an API key may be spent on** must reach the function without a JWT, which in staging is `identity_jwt.api_key_prefixes = ["wpk_"]` on the gate, and in production is the native authorizer refusing the key before the function sees it.

That refusal is the open item this contract records rather than hides. In production, a route behind the native JWT authorizer cannot accept an API key at all. M6 ships API keys working in staging, through the gate's pass-through, and working in production only for the routes whose keys are `authorization_type = "NONE"`, which after this project is `/api/mcp` alone. Making a per-user API key work against the full REST surface in production needs either a Lambda authorizer in front of every route or the native authorizer accepting a second issuer, and both are platform decisions rather than product ones. The upstream ask is at the end of this document.

## Platform gaps

Verified against `webbpulse` 0.43.0 as installed and `terraform-aws-platform-modules` 2.26.0 as resolved by the `~> 2.25` pin. Design section 6's `identity.api_keys`, `identity.scopes.require_scopes`, `identity.oauth_server` and `claims_or_api_key` have all landed and are used here rather than reimplemented, as has the gate's `identity_jwt.api_key_prefixes`.

| Gap | Where | Proposed surface |
|---|---|---|
| An API key credential that works in production | `terraform-aws-platform-modules` | The staging gate passes a prefixed bearer through for the function to verify. The production path has no equivalent: the native JWT authorizer refuses a non-JWT before the function runs, so an API key reaches only routes declared `authorization_type = "NONE"`. `http-api` wants either a `api_key_prefixes` passthrough of its own, backed by a small Lambda authorizer that defers to the function, or documented guidance that API-key routes are declared unauthenticated and verify in process. This is the one thing that keeps M6's REST API keys staging-only. |
| A tenant-scoped `ApiKeyStore` | `webbpulse-python` | `DynamoApiKeyStore` partitions by `key_hash` with a `user_id` index, which cannot answer "every key in this tenant" without a scan. A `tenant_id-created_at-index` on the platform spec, or a documented tenant-partitioned variant, would let a multi-tenant product use the package's store rather than writing its own. Written locally for now in `app/common/db/dynamo/api_keys.py`. |
| An MCP server transport | `webbpulse-python` | Every product that offers MCP writes the same streamable-HTTP JSON-RPC envelope, the same `initialize` and `tools/list` handling, and the same `WWW-Authenticate` challenge. `webbpulse.mcp.build_mcp_router(tools, claims_dependency)` taking a tool registry would close it. | Share links as a credential kind | `webbpulse-python` | A capability token resolving to one row, stored by hash with a TTL, is the same shape in every product that offers public sharing. `webbpulse.identity.share_tokens` beside `api_keys` would close it. |
| ~~The OAuth authorization server's three tables~~ | `terraform-aws-platform-modules` | Closed. 2.27.0 added the gating `oauth_server_enabled` variable in the `users_stream_enabled` style, along with `oauth_server_mcp_resource_url`, and `modules/identity` now creates `oauth-clients`, `authorization-codes` and `oauth-consents` beside the social login pair.
